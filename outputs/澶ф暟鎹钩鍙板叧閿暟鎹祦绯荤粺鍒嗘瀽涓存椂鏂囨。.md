## 2. 总体关键数据流

```text
ClickHouse SODL 数据湖
  -> sodl_ods_info_new
  -> Hive ODS: sodl.*
  -> sodl_dwb_info
  -> Hive DWB: sodl.dwb_sodl_md5_info / domain_info / ip_info
  -> topthreat_hot_stat
  -> MongoDB: db_statistic.tb_original_*_stat

Kafka / soapa 原始日志
  -> default.log_audit_source / default.log_stats_source
  -> log_compress
  -> csc.ods_csc_log_audit / csc.ods_csc_log_stats
  -> audit DWB: md5_info_audit / url_info_audit / domain_info_audit
  -> merge_data.sh
  -> Hive DWB: default.dwb_md5_info / dwb_url_info / dwb_domain_info

Hive 分区支撑
  -> create_hive_partition
  -> 预创建 ODS / CSC graph / SODL / log source 相关日分区和小时分区

FLKF 安全事件
  -> secevent_analyse
  -> Spark 批处理 secevent-to-hive-batch-flkf.jar
```

## 4. 数据流一：SODL 新数据湖 ODS 入湖

### 4.1 输入源

`sodl_ods_info_new` 从 ClickHouse HTTP 接口抽取数据：

| 子任务 | ClickHouse 源表 | ODS 目标路径 |
|---|---|---|
| `dns_log` | `sodl.dns_log` | `/hive/ods/sodl/dns_log/` |
| `endpoint_security_log` | `sodl.endpoint_security_log` | `/hive/ods/sodl/endpoint_security_log/` |
| `http_log` | `sodl.http_log` | `/hive/ods/sodl/http_log/` |
| `network_security_log` | `sodl.network_security_log` | `/hive/ods/sodl/network_security_log/` |
| `sip_iocstat_log` | `sodl.sip_iocstat_log` | `/hive/ods/sodl/sip_iocstat_log/` |
| `url_log` | `sodl.url_log` | `/hive/ods/sodl/url_log/` |

### 4.2 加工机制

- 按小时分区写入 HDFS。
- 输出格式为 Parquet。
- 写入后校验 Parquet `PAR1` 魔数。
- 自动删除 7 天前旧数据。
- 6 个子任务通过 Oozie fork 并行执行。

### 4.3 关键意义

该链路是新数据湖的 ODS 入口。后续 DWB 和热门威胁统计都依赖这些日志表，尤其是：

- `sodl.network_security_log`
- `sodl.sip_iocstat_log`
- `sodl.dns_log`
- `sodl.url_log`
- `sodl.endpoint_security_log`

## 5. 数据流二：SODL ODS 到 DWB 情报宽表

`sodl_dwb_info` 将 ODS 中的不同日志类型按威胁指标聚合到 DWB。

### 5.1 DWB 输出表

| DWB 表 | 输入 ODS | 威胁指标 | 当前状态 |
|---|---|---|---|
| `sodl.dwb_sodl_md5_info` | `network_security_log`、`endpoint_security_log`、`sip_iocstat_log` | 文件 MD5 | 生效 |
| `sodl.dwb_sodl_domain_info` | `network_security_log`、`dns_log`、`sip_iocstat_log`、`endpoint_security_log`、`url_log` | 域名 | 生效 |
| `sodl.dwb_sodl_ip_info` | `network_security_log`、`dns_log`、`url_log`、`http_log`、`sip_iocstat_log` | IP | 生效 |
| `sodl.dwb_sodl_url_info` | `network_security_log`、`url_log`、`sip_iocstat_log`、`http_log` | URL | 已暂停 |

### 5.2 核心加工动作

| 动作 | 说明 |
|---|---|
| 多源合并 | 同类威胁指标从多张 ODS 表 `UNION ALL` 到一张 DWB 宽表 |
| 字段标准化 | 统一 `manage`、`productver`、`srcip/dstip`、`filehash`、`domain`、`url` 等字段 |
| 指标过滤 | 过滤空 MD5、空 URL、空域名；MD5 长度限定 32 |
| URL 标准化 | 使用 `default.calc_url_mask(url)` 去除协议、端口等噪音 |
| 域名提取 | 从 URL 中截取 host，或直接使用 DNS query / IOC domain |
| 域名逐级拆解 | `evil.example.com` 可拆成 `evil.example.com`、`example.com`、`com` |
| 最长黑域名匹配 | 命中多个黑 DNS 标签时，按子域名长度取最精确标签 |
| 威胁情报关联 | 关联黑 DNS、黑 IP、URL 信誉、MD5 情报和标签表 |
| 设备画像关联 | 关联 `default.ods_devicemanager_deviceinfo` 补齐地域、行业、客户画像 |
| 来源标记 | 通过 `src_log` 保留每条记录来自哪张 ODS 表 |

### 5.3 关键维表

| 维表 | 用途 |
|---|---|
| `sri.ods_sri_hashinfo` | MD5 文件情报，补齐文件属性、病毒名、家族等 |
| `sri.ods_sri_ti_tags` | 威胁标签中英文映射 |
| `csc.ods_csc_db_domain_intelligence_tb_domain_reputation_sync` | 黑 DNS / 域名信誉 |
| `csc.ods_csc_tim_db_intelligence_tb_ip_reputation_sync` | 黑 IP / IP 信誉 |
| `csc.ods_csc_db_url_intelligence_tb_url_reputation_sync` | URL 信誉 |
| `default.ods_devicemanager_deviceinfo` | 设备、客户、地域、行业画像 |

### 5.4 关键结论

SODL DWB 是平台最核心的“新中间表”链路。它把不同安全日志统一整理成 MD5、域名、IP 三类可查询、可统计、可下游消费的威胁情报宽表。

当前 URL DWB 已暂停，因此 URL 维度主要依赖旧 audit 链路和热门威胁统计链路，存在口径不完全统一的风险。

## 6. 数据流三：深圳旧日志压缩与 audit DWB

`log_compress` 是深圳旧架构的关键日志压缩和 audit DWB 生成任务。

### 6.1 第一阶段：构建 ODS 中间表

| 子任务 | 源表 | 目标表 | 过滤 |
|---|---|---|---|
| `insert_audit` | `default.log_audit_source` | `csc.ods_csc_log_audit` | 排除 `configserver` |
| `insert_stats` | `default.log_stats_source` | `csc.ods_csc_log_stats` | 排除 `configserver`，限制 `log_app_id` 长度 |

### 6.2 第二阶段：从 audit 日志提取 DWB

| 子任务 | 源表 | 输出目录 | 主要指标 |
|---|---|---|---|
| `dw_md5_info_audit` | `csc.ods_csc_log_audit` | `/hive/dwb/default/md5_info_audit/${mday}` | 文件 MD5 |
| `dw_url_info_audit` | `csc.ods_csc_log_audit` | `/hive/dwb/default/url_info_audit/${mday}` | URL |
| `dw_domain_info_audit` | `csc.ods_csc_log_audit` | `/hive/dwb/default/domain_info_audit/${mday}` | 域名 |

### 6.3 第三阶段：合并到主 DWB 分区

`merge_data.sh` 将 audit 输出移动到主 DWB 分区的 `log_audit/` 子目录：

```text
/hive/dwb/default/domain_info_audit/${mday} -> /hive/dwb/default/domain_info/${mday}/log_audit
/hive/dwb/default/url_info_audit/${mday}    -> /hive/dwb/default/url_info/${mday}/log_audit
/hive/dwb/default/md5_info_audit/${mday}    -> /hive/dwb/default/md5_info/${mday}/log_audit
```

### 6.4 关键结论

旧链路仍承担 `default.dwb_md5_info`、`default.dwb_url_info`、`default.dwb_domain_info` 的 audit 数据补充。它和 SODL DWB 是并行存在的两套中间表体系：

- `default.dwb_*_info`：旧链路主 DWB，来自 audit 日志。
- `sodl.dwb_sodl_*_info`：新数据湖 DWB，来自 SODL ODS。

系统分析时需要重点关注两套 DWB 的字段口径、来源口径、威胁标签口径是否一致。

## 7. 数据流四：热门威胁统计

`topthreat_hot_stat` 每小时统计热门黑域名、黑 URL、黑文件，并写入 MongoDB。

### 7.1 输入源

| 统计 | 输入源 |
|---|---|
| 黑域名热度 | `default.log_audit_source`、`sodl.network_security_log`、`sodl.sip_iocstat_log` |
| 黑 URL 热度 | `default.log_audit_source`、`sodl.network_security_log`、`sodl.sip_iocstat_log` |
| 黑文件 MD5 热度 | `default.log_audit_source` |

### 7.2 输出目标

| 子任务 | MongoDB 集合 | 时间粒度 |
|---|---|---|
| `domain_stat` | `mongo-int.db_statistic.tb_original_domain_stat` | 小时 |
| `url_stat` | `mongo-int.db_statistic.tb_original_url_stat` | 小时 |
| `file_stat` | `mongo-int.db_statistic.tb_original_file_stat` | 天 |

### 7.3 处理框架

```text
shell 脚本
  -> python -m storage day=X hour=Y conf_path=xxx.yaml
  -> 解析 YAML
  -> 执行 Hive SQL
  -> fetchmany(5000)
  -> 过滤空 key / NULL
  -> 转换为 MongoDB UpdateOne
  -> bulk_write，失败最多重试 5 次
```

### 7.4 关键结论

热门威胁统计是平台的运营可视化输出层。它不直接产出 Hive DWB，而是从旧日志源和 SODL 日志源汇总热度，写入 MongoDB 给业务查询或大屏使用。

## 8. 数据流五：分区预创建与调度支撑

`create_hive_partition` 是平台稳定性支撑任务，负责提前创建 T+2 的 Hive 分区和 HDFS 目录。

重点覆盖：

- `default.log_audit_source`
- `default.log_stats_source`
- `sodl.dns_log`
- `sodl.endpoint_security_log`
- `sodl.http_log`
- `sodl.network_security_log`
- `sodl.sip_iocstat_log`
- `sodl.url_log`
- `csc.ods_csc_vertex`
- `csc.ods_csc_edge`
- 多个 `sri.ods_sri_*` 日分区表

该任务失败时 workflow 仍会到 End，因此它的失败可能不会直接阻塞调度，但会在后续写入链路中表现为分区或目录缺失问题。

## 9. 数据流六：FLKF 安全事件链路

`secevent_analyse` 属于 FLKF 环境，按小时运行 Spark 批处理：

```text
secevent-to-hive-batch-flkf.jar
  -> Spark on YARN client
  -> 处理前 1 小时数据
  -> 写入 Hive
```

该链路和深圳 SODL / log_compress 主链路相对独立，但同属大数据平台调度体系。

## 10. 现状问题和业务影响

| 问题 | 影响 |
|---|---|
| 新旧两套 DWB 并存 | 下游查询需要明确使用 `default.dwb_*` 还是 `sodl.dwb_sodl_*`，否则统计口径可能不一致 |
| `dwb_sodl_url_info` 已暂停 | SODL 新链路 URL DWB 缺失，URL 分析可能依赖旧 audit 或 topthreat 统计 |
| `log_compress` 旧 DW 任务已注释 | 旧架构只保留 audit 路径，非 audit 的旧 ODS 多源 DW 不再产出 |
| domain_info 只保留黑域名或顶级域名 | 该表不是全量域名日志，下游不能用它做普通域名访问全量分析 |
| topthreat file 只来自 `log_audit_source` | 热门文件统计未纳入 SODL `network_security_log` / `sip_iocstat_log` |
| `create_hive_partition` 失败仍 End | 分区问题可能延迟暴露到实际写入任务 |
| URL 配置文件名 `blcak_url_stat.yaml` 拼写异常 | 自动化维护、检索、配置生成时容易误判 |

## 12. 面向后续系统分析的重点问题

1. 下游业务分别使用哪些表：`default.dwb_*_info`、`sodl.dwb_sodl_*_info`、MongoDB `tb_original_*_stat`。
2. URL 新链路暂停后，下游 URL 统计是否仍满足业务需求。
3. topthreat 的输入源是否需要和 DWB 口径统一，尤其是文件 MD5 热度是否需要纳入 SODL。
4. domain_info 的“只保留黑域名/顶级域名”是否被所有使用方理解。
5. `create_hive_partition` 失败是否需要报警，而不是静默进入 End。
6. 新旧链路里的维表关联逻辑是否一致，尤其是 family/category 标签和设备画像字段。
