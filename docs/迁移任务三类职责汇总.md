# 迁移任务三类职责汇总

日期：2026-09-10。主分类依据任务职责；输入数据、处理复杂度和输出位置作为辅助标签。

## 1. 数量和职责

| 主类别 | 数量 | 定义 | 建议责任边界 |
|---|---:|---|---|
| 一、平台数据接入 | 6 | 外部数据进入平台原始表、维表或图数据表 | 可交数据湖承接，逐任务确认；兼有ES/Nebula等输出需单独交接 |
| 二、平台内数据加工 | 2 | 平台原始数据与维表加工成中间表或主题结果 | 可由数据湖承担，也可由业务方维护；按保留的加工子任务确认 |
| 三、业务消费与同步 | 23 | 从平台获取数据，经选取或业务加工，写入外部系统、文件或供业务使用 | 含用户确认通过SQL查询Hive的2项，暂按业务消费归类，输出职责待核实；逐项确认保留状态及验收人 |
| 需单独核定迁移方式的条目 | 14 | 7个旁路业务、2个平台维护任务、5个已下线/可下线 | 仍纳入项目跟踪，不代表无需三区迁移；不计为新增的业务主类别 |
| 合计 | 45 | 沿用任务清单去重口径 | 分类数量不等于最终需迁移数量 |

同一任务包含多种职责时按主输出归类，并标注兼有职责。log_compress按平台内加工计1项，实施时拆除已取消的压缩入库步骤，只评估必要DWB加工。三类并不意味着三个部门已经接受任务，移交仍待双方确认。

### 4.2 分类依据和验证边界

压缩表属性依据现有log_compress写入逻辑与消费者SQL/来源清单的对应关系，不依据csc库名。DWB属性依据加工说明及来源清单。这里的原始日志包括平台接入的SODL日志，不意味着未经任何上游处理的设备原始报文。

同一服务含多个SQL时，执行台账应继续拆为“任务 -> SQL/子任务 -> 输入表及层级 -> 输出 -> 验证用例”。新旧查询结果对账与Mongo/Redis/Kafka等目标读回验证分别记录；只通过SQL验证不能代表整条同步链路通过。

## 6. 后续跟踪方式

统一字段：主类别、输入表、处理方式、输出实例/库/Key/Topic、保留状态、承接方、缺失依赖、生产结果校验、消费转换校验、目标读回校验、切流状态。

推进顺序：确认前两类的交接与数据契约 → 第三类按输入具备情况分批改源 → 验证结果和性能 → 验证目标读回 → 业务验收和切流。前两类已交数据湖且输入可用的，第三类无需等待其他无关接入或模型完成。
