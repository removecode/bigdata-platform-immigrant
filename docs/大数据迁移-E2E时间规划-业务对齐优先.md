# 大数据迁移E2E时间规划：业务对齐优先

编制日期：2026-09-15。状态：排期建议，阶段工期及人员投入待确认；“先业务对齐、明确迁移或下线”已由用户明确。

基准：此前指定版本的《大数据迁移-E2E规划-指定版本-执行计划已更新.xmind》；结合45项任务SQL核对结果及DEC-001两表下线决策。本时间规划优先于旧导图中的11天准备、12天执行估算；旧图保留为参考，不代表其任务数量和待补资料状态仍是最新。

## 工期口径与资源假设

- D1为项目启动后的第一个工作日，尚未指定实际开工日。D序号仅累计项目工作日，不是自然日；另列的观察期为自然日，不计入D序号。节假日及调休按团队工作日历落日期。
- 建议基线：25个工作日完成最后一批切换，观察至少7个自然日，再用2个工作日完成退出确认，即27个工作日加至少7个自然日。无额外长假时约6—7周。
- 假设可投入2名任务开发、1名测试/数据验证人员，项目推动者持续协调；数据湖及运维/DBA有明确接口人并按批次交付。以上均为估算条件，不是已确认资源。
- 数量基线为45项盘点对象，包含历史已下线和待确认任务；实际迁移数量在业务对齐后形成，不按45项全部改造估算。
- D5形成范围基线，D10用试点实测和数据湖交付承诺重新估算剩余工期。业务范围、人数、共享数据就绪时间变化均需要追加调整记录。
- 观察不少于7个自然日且覆盖约定业务周期。低频任务需等实际周期或完成业务认可的等价演练，不能仅凭7天无告警验收。

## 已知问题纳入首轮确认

- DEC-001：租户订阅表与skyeye IP表可下线。ctig-report-data-analysis-prc、attack-ip-analysis-cronjob存在明确SQL引用，需处理相关逻辑；black-ti-context-produce-prc仅手工来源标注租户表；datax-server涉及两个同步子任务。
- 全量SQL核对：45项中19项已提供SQL表集合一致，4项差异、3项缺手工来源、2项动态/截断、1项库名待确认、16项没有SQL正文可核对。16项不一定都应有SQL，需按非SQL接入、维护或资料缺失分别核实。
- yara与sp在当前材料中已有SQL，不能沿用旧导图“补SQL”的笼统待办；仍要核实现网版本和手工来源。
- 不把audit/stat已交付等同于SODL、基础表、DWB及下游目标就绪。
- log_compress取消后，保留业务必要的映射、聚合和过滤须有等价实现；不得直接重建已取消压缩任务，也不能因取消任务而丢失业务逻辑。

## 批次执行与硬依赖

- 原始日志/业务基础表直接消费：所需输入和目标就绪后，优先选择改造较小、可完整验收的保留任务试点。audit/stat直接消费是否可单独构成批次，按实际SQL和混合分支核实，不设空里程碑。
- 中间结果依赖：原始日志与维表就绪 → 必要中间加工生成并验收 → 下游任务E2E验收 → 切换观察。独立模型可并行。
- 压缩表依赖：原始表字段与口径确认 → SQL/必要加工改造 → 规模性能验证 → 输出和业务验收 → 切换观察。应在试点期暴露性能风险，不留到最后。
- 退役事项：业务批准 → 处理保留消费者依赖 → 停止获批调度并观察 → 保留期交接。独立且已确认无消费者的退役项可以提前完成。
- 分批依据是依赖就绪、风险与业务窗口；业务领域用于组织验收，不能用业务分类覆盖技术依赖。

## 验收与回滚安排

- D3起定义同一完整数据窗口、维表版本及可重置目标初始状态。测试环境缺旧Hive时，采用获准生产快照/结果重放，记录快照截止点与迟到边界。
- 查询及中间结果对账：业务键、字段、过滤/关联/聚合、更新删除及完整发布；结果差异按输入、加工、输出分层定位。
- Mongo：读回业务键与文档，覆盖新增、更新、删除、重试；Redis：Key、值类型、值、TTL与旧Key清理；Kafka：消息键/内容、重复/顺序及实际消费结果。
- 延续质量方案A的离线对账思路，必须补齐E2E；状态型输出需隔离目标验证实际写入和读回。若需持续双跑，按批评估资源，不默认新旧写同一生产目标。
- 切换前完成性能与恢复演练；切换按批次/位点边界且同范围单写者。异常停新写、恢复或补偿目标数据、恢复旧任务与读取、补边界对账；Kafka已消费副作用需补偿。
- 旧供数、任务版本和必要数据在观察/恢复期保持可恢复，共享上游必须等全部保留消费者退出后再停止。

## 推动节奏、耗时与提效

- 每日15分钟更新交付、差异、负责人及预计解除日期；关键共享依赖阻塞超过1个工作日时升级协调，作为建议管理规则。
- 每周两次集中处理业务去留与数据湖交付争议，避免开发人员逐任务重复追问。
- 复用表级交付验收、固定输入、SQL适配模板、批量对账、Mongo/Redis/Kafka读回与报告生成。先验证代表任务，再扩批；复杂逻辑人工评审。
- 最大工期变量：业务未决、数据湖交付、三区目标缺失、历史回填、压缩改原始的性能、中间模型差异及低频业务观察。
- 汇报分别列等待时间、人工改造时间、数据运行时间。每批展示确认保留数、输入就绪数、E2E通过数、已切换数、观察完成数，任务不重复计完成。
- D10试点后发布修订排期：按剩余改造工时/可用人员、数据交付日期、验证吞吐及业务窗口估算，不以任务个数均摊工期。

## 需落实的排期输入

实际开工日、可投入人员与并行能力、各业务负责人及验收人、数据湖逐表日期、三区目标实例安排、切换窗口、假期安排及低频业务周期均待确认。上述缺项不会阻止D1业务盘点，但会影响最终完成日期承诺。
