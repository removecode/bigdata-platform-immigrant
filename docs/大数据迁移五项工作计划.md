# 大数据迁移五项工作计划

更新日期：2026-09-22  
适用范围：依赖旧Hive、拟迁移到StarRocks（SR）的业务生产、查询、同步与运营任务。

## 一、总体安排

项目拆为五个相互衔接的工作包：

```text
① 业务分类与范围确认
       ↓ 决定迁什么、谁验收
② 验证环境与质量方案
       ↓ 决定在哪里、怎样证明正确
③ SR连接与运行兼容性
       ↓ 解决任务能否运行（当前已完成基础验证）
④ 现网数据与基线收集
       ↓ 为新旧SQL同输入对账提供样本和基准
⑤ 分批上线与持续运营
       ↓ 影子验证、切流、观察、回滚及旧链路退出
```

五项工作不是完全串行：业务分类确认后，SR连接验证、现网数据收集和首批依赖交付可以并行；上线运营方案必须在首批切流前准备完成。

## 1. 业务分类迁移计划

### 1.1 目标

将45项盘点任务逐项归入迁移、仅验收新供数、无需改造、退出或待确认，按业务领域组织负责人和验收场景，按数据依赖决定实际迁移顺序。

### 1.2 迁移顺序

| 批次 | 业务范围 | 主要任务/说明 | 放行前置 |
|---|---|---|---|
| P0 | 范围与退出对齐 | 可下线、待确认、已下线及混合状态任务 | 业务负责人、读取者、验收人和退出审批明确 |
| P1 | 三类代表任务试点 | `gnn-domain-hive-query-cronjob`、`cipd-product-resource-monitor-prc`、`filter-layout-ip-seg-stat-prc` | IOC点表、stat、audit及IP信誉等相应输入可用 |
| P2 | 热度、活跃度与统计库 | 5项 | audit、SODL、必要DWB等价结果按分支交付 |
| P3 | 情报质量与误报漏报 | 4项，含已确认退出的phishing任务 | Domain/MD5模型及Mongo/Redis验证通路 |
| P4 | 情报生产、研判与分发 | 12项，拆为图数据、SODL、DWB/混合来源、旁路分发 | 点边表、SODL ODS、必要DWB和维表 |
| P5 | 报告、样本查询与上报 | 5项，先确认3项去留 | 基础表、动态维表、接收方和上报窗口 |
| P6 | 运营展示与运行监控 | 6项 | 上游统计口径稳定，页面/指标实际读取可验收 |

公共数据接入、加工与维护10项不排成最后一个业务批次，而是作为P1至P6的并行前置泳道。某张表或某个加工未就绪时，仅阻塞其消费者。

### 1.3 交付物

- 45项任务去留与责任矩阵。
- 任务—SQL—输入表—输出目标—业务读取者映射。
- 分批清单、批次进入条件和完成门槛。
- 数据湖交付清单：物理表、字段、历史、增量、完整截止点、SLA和负责人。
- 下线清单：审批人、停调度时间、观察期、回滚窗口和依赖核查结果。

详细任务计划见[《业务分类迁移计划（917版）》](./业务分类迁移计划-917版.md)。

## 2. 测试环境搭建与生产环境验证方案

### 2.1 两种方案对比

| 维度 | 在测试环境搭建旧Hive | 在生产环境验证旧Hive与新SR |
|---|---|---|
| 隔离性 | 高，可自由构造、清理和重复执行 | 中，需要只读账号、资源组、限流和执行窗口 |
| 数据真实性 | 依赖拷贝或构造，难完整复现迟到、脏值和规模 | 高，能够覆盖真实数据分布、历史问题和峰值规模 |
| 新旧输入一致性 | 难度高，需要同步相同数据和动态维表 | 较容易，可固定同一历史窗口和数据截止点 |
| 建设成本 | 高，要建设旧平台、数据装载、权限、运维和版本匹配 | 较低，无需复制旧平台，但需打通生产只读通路并完成合规审批 |
| 前置验证能力 | 强，适合异常、边界和破坏性测试 | 受限，不适合随意构造或改写生产数据 |
| 性能可信度 | 若规模不足，性能结论有限 | 高，更适合验证原始表替代压缩表后的扫描量与耗时 |
| E2E输出验证 | 可连接隔离Mongo/Redis/Kafka完成 | 不宜直接写生产目标，应使用影子库、Key、Topic或指标命名空间 |
| 主要风险 | 建设周期长、数据保真度不足、维护成本可能超过迁移收益 | 查询资源影响生产、访问合规、误写生产目标、动态数据造成对账假差异 |

### 2.2 推荐方案：混合验证，不复制整套旧Hive

当前测试环境没有旧Hive，而生产环境同时有旧Hive和新SR。结合投入产出，建议：

1. **生产环境做固定窗口只读对账**：旧Hive和新SR使用相同具体日期/小时、截止点、维表快照与参数；只输出验证文件或验证表，不写生产业务目标。
2. **测试或隔离环境做代码与E2E验证**：验证Python 2任务运行、参数计算、SQL生成、异常重试，以及写入影子Mongo/Redis/Kafka/Prometheus后的读回和业务读取。
3. **不以搭建完整旧Hive作为放行前提**：只为无法在生产安全验证的特殊逻辑构造最小数据集，不建设一套长期维护的旧平台复制品。
4. **性能测试放在生产规模受控窗口**：使用专用资源组、扫描限制、超时和错峰窗口，重点验证取消压缩表后的原始表查询。

### 2.3 质量放行门槛

- 输入层：新旧窗口、数据截止点、动态维表版本一致；分区/时间、行数、业务键、空值和解析失败摘要可解释。
- SQL层：过滤、JOIN、去重、聚合、自定义函数及VARCHAR转换结果一致。
- 输出层：Mongo文档、Redis Key/TTL、Kafka消息或Prometheus指标写入和读回正确。
- 业务层：真实查询、页面、接口、报告或过滤包场景通过。
- 性能层：时延、扫描量、资源、并发及补数窗口满足SLA。
- 回滚层：旧任务、旧输入和目标恢复/补偿方法已演练。

## 3. SR连接与Python 2兼容性

### 3.1 当前进展

- SR连接已经实测成功。
- 现有Python 2运行环境已验证能够完成本次所测连接。
- 该项可从“连接阻塞”转为“已完成基础验证”，首批任务可以进入SQL级兼容验证。

### 3.2 证据边界

“Python 2能够连接SR”不等于以下内容已全部通过：

- 所有项目使用的驱动版本、连接参数和认证方式均兼容。
- Hive/Trino SQL方言可以原样在SR执行。
- UDF、LATERAL VIEW、JSON、正则、数组、日期及分区语法兼容。
- 全字段VARCHAR下的比较、排序、JOIN和数值聚合正确。
- 连接池、超时、重试、游标、字符集和大结果集行为满足生产要求。

### 3.3 首批仍需补测

| 检查项 | 最小用例 | 通过标准 |
|---|---|---|
| 查询参数 | 日期、字符串、数字、空值及特殊字符绑定 | 无格式化异常、注入风险或类型误判 |
| VARCHAR解析 | 普通数字串、空串、`NULL`、Mongo Extended JSON | 解析失败可识别，业务值符合预期 |
| 大结果集 | 分批拉取、游标关闭、内存占用 | 无OOM、泄漏或连接长期占用 |
| 网络异常 | 超时、断连、重连、查询取消 | 重试不造成重复业务写入 |
| 字符集 | 中文、URL、JSON、转义符 | 查询和目标端写入不乱码、不截断 |
| 并发与资源 | 同时运行代表任务 | 连接数和查询资源满足限制 |

## 4. 现网数据收集

### 4.1 收集目的

现网数据不是为了复制整个平台，而是用于建立新旧对账输入、业务预期、性能基线和异常测试集。收集必须最小化、可追溯，并遵守生产数据使用和脱敏要求。

### 4.2 每个任务应收集的六类材料

| 类别 | 收集内容 | 用途 |
|---|---|---|
| 调度参数 | 实际`day/hour/start/end`、时区、T-1/T-2计算、补数参数 | 锁定新旧SQL相同输入窗口 |
| 输入摘要 | 分表/分区行数、业务键数、最早/最晚时间、空值、重复和解析失败 | 先判断差异来自供数还是SQL逻辑 |
| 动态维表快照 | 信誉、标签、Hash、设备、自定义上传等表的快照时间或版本 | 避免两次查询间维表变化造成假差异 |
| 旧结果基线 | 旧SQL结果、旧Mongo/Redis/Kafka/指标输出、业务读取截图或响应 | 作为迁移预期和回归基线 |
| 性能基线 | 数据量、扫描量、耗时、队列等待、失败率、补数时长 | 判断原始替代压缩后的性能是否达标 |
| 异常样本 | 新增、更新、删除、空值、脏值、迟到、重复、极值、部分失败 | 验证VARCHAR解析、幂等、重试和补偿 |

### 4.3 收集优先级

1. P1三项代表任务的固定窗口输入、旧结果和输出目标样本。
2. P2中`topthreat_hot_stat`三个SQL分支及原始替代压缩的性能样本。
3. P3/P4涉及DWB、SODL和动态维表的分层样本。
4. P5报告/上报接收结果和P6展示/指标基线。

### 4.4 收集规则

- 每份快照附任务名、SQL版本、表名、时间窗口、截止时间、导出时间和责任人。
- 大数据只保存摘要和必要差异明细；包含敏感字段时脱敏并限制访问。
- 旧结果与新结果使用不可变批次号关联，禁止用执行时的“今天/昨天”作为唯一描述。
- 收集脚本只读、限流、可审计；不得借数据收集直接修改生产目标。
- 结果文件设置保存周期，迁移验收和争议窗口结束后按数据规范处置。

### 4.5 完成标志

每个待迁任务均具备一份“对账参数单＋输入摘要＋旧结果快照＋性能基线＋异常样本”，首批三项优先齐套。

## 5. 上线后的运营方式

### 5.1 分阶段运营

| 阶段 | 建议时长 | 运行方式 | 主要动作 |
|---|---:|---|---|
| 影子验证 | 切流前 | 旧任务保生产，新任务只计算或写隔离目标 | 自动对账、目标读回、业务试读、性能和回滚演练 |
| 切流窗口 | 按任务审批 | 同一业务范围保持单一生产写者 | 固定批次/位点，暂停或切换旧写者，验证首批结果 |
| 强观察期 | 至少7个自然日 | 新任务正式生产，旧任务保留可恢复能力 | 每日对账、告警巡检、业务确认、问题日清 |
| 稳定运营期 | 长期 | 新任务常态运行 | SLA、成本、容量、数据质量和变更管理 |
| 旧链路退出 | 观察通过后 | 先停调度，再撤权限/资源，最后归档 | 依赖扫描、审批、回退窗口结束、资产清理 |

### 5.2 上线后必须监控的指标

- **任务运行**：成功率、开始/结束时间、重试次数、连续失败、积压和补数状态。
- **输入质量**：数据量突增突降、完整截止点、迟到量、关键字段空值和VARCHAR解析失败率。
- **业务结果**：业务键数、核心指标、旧基线偏差、Top N变化、报告/页面/接口可用性。
- **输出目标**：Mongo写入/更新/删除、Redis Key数量与TTL、Kafka生产与消费积压、Prometheus指标新鲜度。
- **性能资源**：SR查询时延、扫描行数/字节、CPU/内存、并发、超时及对其他生产负载的影响。

### 5.3 每日运营节奏

1. 自动生成前一周期任务运行和数据质量摘要。
2. 强观察期内对关键任务执行固定口径对账，差异自动分级。
3. 任务技术负责人处理运行和数据问题，业务验收人确认业务影响，数据湖处理上游供数问题。
4. P0/P1问题当日升级；普通差异形成负责人、原因、处理时限和补偿范围。
5. 每批第7日召开退出评审：决定通过、延长观察或回滚，不以“没有收到投诉”代替验收。

### 5.4 异常与回滚

```text
发现关键异常
  → 停止新任务继续写入
  → 冻结并定位影响批次/业务键
  → 恢复或补偿Mongo/Redis/Kafka/指标状态
  → 恢复旧任务和旧读取路径
  → 对切流边界补做新旧对账
  → 修复后重新走影子验证与审批
```

Kafka已经被消费的消息通常不能仅靠切回旧任务恢复，需要业务消费方参与去重或补偿；Mongo/Redis必须恢复到正确状态，而不只是恢复任务进程。

### 5.5 旧链路退出门槛

- 强观察期通过且业务验收人签字。
- 无未解释关键差异，无未处理目标端副作用。
- 全局扫描确认没有保留任务继续读取旧Hive表、压缩表或旧DWB。
- 回滚窗口结束，历史补数和审计数据可追溯。
- `datax-server`、`sync-mongo2hive-job`、`secevent-to-hive-stream-prc`等替代供数已逐表验收；混合服务只退出获批子任务。
- 停调度、撤权限、释放资源和文档归档按顺序完成，不直接删除旧数据或配置。
