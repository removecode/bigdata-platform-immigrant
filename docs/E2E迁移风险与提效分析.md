# E2E迁移风险、耗时与提效分析

日期：2026-09-10。
依据：45项任务分类、现有来源输出清单、用户确认及[端到端执行推演](端到端迁移执行推演.md)。下述排序是规划判断，不是现网测量结论；没有资源、数据规模和试点证据前不报固定人日或完成日期。

## 1. 总体判断

本项目要覆盖“日志/Mongo等源数据 -> 接入新平台 -> 必要中间加工 -> 业务查询与转换 -> Mongo/Redis/Kafka/文件等输出 -> 实际业务读取 -> 观察与旧依赖退出”。仅查询改源成功不能证明业务无影响。

最可能决定日历工期的是共享输入及历史数据交付、三区目标环境、业务/承接决策和观察窗口；最可能消耗人工的是新旧差异定位、必要中间结果语义适配、状态型目标校验与恢复。多数简单SQL可能只需小改，但必须试点验证，不能把23个消费服务等同23条SQL或23份同等工作量。

audit/stat已迁，但交付验收未在本项目验证；新平台没有压缩表和中间表。SODL六张日志、Mongo接入表、其他维表及业务表的交付不能据此推定完成。接入6项、加工2项是否交数据湖仍需逐项确认。

## 3. 最耗时的地方：区分三种时间

同一事项可能同时包含等待、人工和机器运行时间。以下为优先调查顺序，不是确定的耗时排名。

| 顺位 | 事项 | 主要时间类型 | 为什么可能长 | 如何缩短或尽早暴露 |
|---|---|---|---|---|
| 1 | SODL、hashinfo/其他维表、三区Mongo与模型承接交付 | 跨团队等待 + 实施 | 一个缺口可能阻塞多个消费者；字段/历史/责任不清会反复沟通 | 启动即并行发逐项交付单，标受影响任务、负责人、日期和可验收标准；逾期升级 |
| 2 | 新旧差异定位与结果口径确认 | 人工 + 反复执行 | 输入不齐、维表变化、旧SQL版本不同会让每轮差异都变化 | 固定可复现窗口和版本；先查共享输入，再查加工和写入；集中记录差异结论 |
| 3 | 必要中间结果的等价实现与性能调整 | 人工 + 运行 | DWB涉及多源、关联、聚合和函数；原始字段存在不代表结果可直接替代 | 先确认保留结果，共享逻辑统一实现，代表模型试点；不重建无用途模型 |
| 4 | Mongo/Redis等状态型输出验证及回退 | 人工 + 环境等待 | 需要初始状态、更新删除、重试补数与读取者协同；不是比行数 | 尽早建立影子目标和已知初始状态，复用读回工具；提前做补偿演练 |
| 5 | 历史回填、增量追平与全量对账 | 机器/网络运行 + 排队 | 受存储扫描、带宽、导入、限流及线上负载限制，数据保留期可能不足 | 按真实最长消费窗口确定历史范围，分片检查点与增量追平；申请容量并记录进度 |
| 6 | 业务确认、切流窗口和周期观察 | 决策等待 + 业务周期 | 验收人缺失、低频任务和业务窗口不是增加开发就能解决 | 启动时定验收人和窗口；小批切流，认可的历史回放辅助覆盖低频场景 |

历史准备可能成为最长项，但目前没有数据量、吞吐和保留期证据，不能直接认定。若稳定有效回填吞吐为R、待回填量为D，可用D/R估计纯回填下界，另加排队、重试、校验和增量追平；若处理增量的能力不超过新增速度，积压无法收敛，不能承诺切换日期。

## 4. 关键路径：先解决阻塞整条链路的事项

单条分支的验证开工取决于“必要输入、环境、业务规则、可运行代码”全部具备的最晚时间，而非这些准备工作全部串行相加。影子验证之后仍有正式切流窗口和观察期。批量发布和共享人力会进一步影响排期。

| 代表分支 | 潜在关键路径 | 可以提前并行 |
|---|---|---|
| filter-layout-ip-seg-stat-prc | audit口径/IP信誉就绪 -> 查询等价 -> Redis状态/业务读取验证 -> 切流观察 | SQL盘点、映射模板、Redis影子目标和用例准备 |
| 保留的SODL DWB消费者 | 所需SODL日志/维表及责任落实 -> 必要DWB结果 -> 消费与目标验证 -> 切流观察 | 消费SQL适配、输出验证工具、业务规则确认 |
| cert-app-samplesync-job等hashinfo消费者 | Mongo接入交付与历史/增量验证 + business_data等输入就绪 -> 导出及实际接收验证 -> 切换 | 文件格式用例、接收端环境、SQL兼容检查 |

其他输入缺失不能通过删除JOIN或忽略数据分支来绕过。允许过渡访问旧平台时明确风险、结束日期和退出责任，不能计为已无旧依赖。

## 5. 最有价值的提效措施

| 提效措施 | 具体执行 | 节省什么 | 不可省略的边界 |
|---|---|---|---|
| 业务去留前置 | 先确认待定任务、模型和真实消费者，确认退役后再移出开发范围 | 无用改造和验证 | 未答复不等于同意下线 |
| 按共享输入组织工作 | audit/stat、SODL、hashinfo、信誉/设备等各有交付与验收负责人，挂关联SQL清单 | 重复协调和重复查输入差异 | 表级验收不能代替各消费者业务验收 |
| 先试点最小改源 | 代表简单查询、压缩映射、DWB复杂查询和目标写入分别试跑 | 避免全量过度重构，形成可信估算 | 不能只用最简单任务外推全部工作量 |
| 参数化批量验证 | 共用窗口/版本配置、比较器、错误分类和证据报告，SQL级执行 | 手工跑SQL和人工比结果 | 每任务业务键、容差、重复与空值语义独立确认 |
| 批量自动化迁移（待建设） | 配置与依赖图驱动预检、模板适配、测试部署、自动验收及发布包生成，审批后分批切流 | 重复配置、部署、验证和发布操作 | 复杂逻辑人工评审；限并发、幂等、失败暂停；生产切流不跳过批准 |
| 前期交付E2E测试环境 | 本批输入到实际业务读取全链路可运行、写入隔离、初始状态可重置、日志报告可追溯 | 环境断点和联调阶段反复等待 | 冒烟证明环境能力，不代替结果验收及生产规模验证 |
| 共享加工只实现一次 | 对重复使用的必要DWB语义统一实现并版本化 | 重复编码和口径漂移 | 是否集中生产取决于复用与性能，不一律建全套模型 |
| 影子输出提前建 | 查询改造和Mongo/Redis/Kafka隔离环境同时推进 | 等到联调才发现数据库缺失的等待 | 真实转换/写入/读回及业务读取仍需验证 |
| 差异按层定位 | 输入 -> 模型 -> 查询转换 -> 目标 -> 业务；同一根因关联全部受影响任务 | 重复排障和无效重跑 | 不靠扩大容差或去掉困难字段制造通过 |
| 依赖齐备即小批推进 | 不等全部表或全部三区实例；相关目标未好先做只读验证 | 全局串行等待 | 不把局部通过计为整任务切流完成 |
| 历史范围按需求裁定 | 收集最长回看/补数/合规保留要求再定回填量，支持分片续跑 | 无必要全历史搬运和失败重跑 | 不能擅自缩短业务或恢复所需历史 |
| 变更尽量解耦 | 在可接受的过渡方案下分开验证引擎改源与目标实例变更；版本和配置可追溯 | 差异归因和回退复杂度 | 跨区访问须获批；数据正确但业务路由未切不算完成 |

第一阶段只建设足够支持此次迁移的对账配置和工具，不先造通用数据质量平台。工具本身用“故意漏写、重复、改字段、TTL错误”等已知失败样例验证，防止自动化系统误报通过。

## 6. 时间与效率如何衡量

试点至少采集简单改源、压缩表映射、必要模型复杂查询以及适用输出端的真实样本。记录每项实际人工耗时、外部等待、执行耗时、差异定位轮次和首次通过率，再按实测复杂度分组估工，不用服务数平均分摊。

每项状态记录进入/退出时间、阻塞原因与解除人；整任务进度同时记录SQL覆盖度和业务验收。可并行时间不要重复累计为项目日历工期；共享工程师的任务也不能假定无限并行。

| 指标 | 用途 |
|---|---|
| 未交付共享输入、受影响保留任务数、最早需用日期 | 识别阻塞面和优先协调顺序 |
| 业务待决项及等待天数 | 防止无用开发和无限待定 |
| SQL直接通过/需映射/需逻辑改造/依赖阻塞数量 | 形成有证据的开发估算 |
| 未解释差异数量、重跑轮次、已复用根因修复数 | 发现验证低效与共享问题 |
| 各类目标端验证及业务读取通过数 | 防止只报SQL完成率 |
| 待回填量、实测吞吐、增量积压/延迟、资源利用率 | 判断历史追平是否可收敛 |
| 已切流、观察完成、仍依赖旧平台任务数 | 区分业务迁移和平台退役进度 |

## 7. 推动者近期优先级

1. 优先把共享输入和目标环境列为具名交付项：SODL、hashinfo/DataX、信誉/设备等维表、三区Mongo及必要模型承接；先确认现状再锁日期。
2. 与业务定下去留、验收规则和真实读取者，约定决策截止与升级人；不以沉默作为批准。
3. 选依赖齐备的代表任务建立可复现对账基线与影子写入样例，批量验证失败按层归因。
4. 以试点证据重估编码、验证、历史准备、外部等待和观察时间，列各分支关键路径。
5. 切流评审只认输入/加工/查询/目标/业务证据以及回退能力；不为进度跳过生产保护措施。

本分析提出的是计划和待验证风险，没有执行生产查询、修改数据库、触发同步或切流。
