# 云脑大数据平台需求分析（使用方诉求）

**文档日期：** 2026-06-24  
**文档立场：** **使用方**（平台运维、运营）— 描述当前怎么用、痛在哪、要什么体验与指标  
**不涉及：** 底层技术选型、组件设计、由谁开发、如何实现  
**材料来源：** `log/DATA_FLOW.md`、`outputs/运营诉求 xlsx`、`outputs/换盘数据.md`、`Q&A/16–17`

---

## 1. 文档说明

本文只回答三件事：

1. **我们现在怎么在用平台**（频次、场景、依赖哪些数据）
2. **用起来哪里痛**（有材料依据）
3. **我们要求平台方交付什么体验与指标**（可验收，与实现方式无关）

平台怎么建、用什么引擎、是否迁湖仓，**由建设方决定**；使用方只关心：**能不能查、几点能查、查多久、挂了知不知道、别让我们猜表名**。

---

## 2. 我们是谁、依赖什么

| 角色 | 日常在平台上做什么 |
|------|-------------------|
| **运营** | 查鉴定/主探/沙箱/合规日志，查 hash/IP/域名热度，做处理量统计、时延分析 |
| **运维** | 保障日批数据按时可用，处理「查不到数」、磁盘故障后的恢复，配合平台变更 |

**共同前提：** 平台处在新旧数据并存期，**同一类问题可能对应不同数据集**（见 §6 查表对照）。使用方需要平台方给出**明确的「场景 → 去哪查」说明**，而不是让我们记 Hive 表名。

## 3. 当前使用情况

### 3.1 运营：23 条固定查询诉求

| 维度 | 现状 |
|------|------|
| 总数 | **23 条** |
| 执行方式 | **手工 18 条** + **临时脚本 5 条**，无统一入口 |
| 时间范围 | **22/23** 按近一月；**1 条**按单日 |
| 强依赖日批 | **19/23** 依赖「昨日审计/统计类数据」产出后才能查 |

**按主题：**

| 主题 | 条数 | 频次概况 | 典型用途 |
|------|------|---------|---------|
| 文件/样本/hash | 8 | 含 3 条多次/天（热度） | 鉴定状态、云查日志、上报通道 |
| IP 主探/信誉/时延 | 8 | 多条多次/周；#22/#23 为脚本 | 过滤日志、降误报、未检出、P95 时延 |
| 沙箱/流量送检 | 3 | 多次/月 | 送检记录、IOC 检出、处理量 |
| URL/域名/合规 | 3 | 多次/周 | 合规过滤、URL 联查、域名热度 |
| 多引擎处理量 | 1 | 1 次/月 | 引擎 cost 统计 |

> 来源：xlsx「原始诉求结构化」「共性诉求」

### 3.2 运维：当前保障方式

| 维度 | 现状 |
|------|------|
| 日批数据 | 每日凌晨前后产出「昨日」审计/统计类数据；上午运营开始查 |
| 热度类数据 | 部分场景依赖更晚才就绪的宽表（IP/域名热度） |
| 故障感知 | 任务是否成功需多处查看；分区类问题常**晚才发现** |
| 基础设施 | 2026 年 5–6 月磁盘拔插 **8/10 次**；曾发生**任务全停**；换盘处置记录 **14.5h+** |
| 人力 | 可归入大数据平台的投入约 **129.5h**，大量用于保障与排障 |

> 来源：换盘文档、`DATA_FLOW.md`、`Q&A/17`

### 3.3 使用方已知的数据限制（不是需求，是约束）

迁移未完成，**四类威胁指标不能假设任意入口都有：**

| 类型 | 新链路 | 旧链路 |
|------|--------|--------|
| MD5 / 域名 | 有 | 有 |
| URL | **无**（新侧暂停） | 有 |
| IP | 有 | **无**（audit 无 IP 宽表） |

使用方需求：**平台方须书面告知每个场景用哪条链路**，避免我们猜错表。

> 来源：`Q&A/16`

## 4. 当前痛点（使用方视角）

### 4.1 运营

| # | 痛点 | 我们感受到的 |
|---|------|-------------|
| O-1 | 没有统一入口 | 每人维护 SQL/脚本，新人上手难 |
| O-2 | 不知道能不能查 | 日批失败仍去查，空跑浪费时间 |
| O-3 | 不知道查哪 | 热度、明细、hash 不在同一套数据里，易查错 |
| O-4 | 等待无预期 | 近一月查询有时很久，不知道是否正常 |
| O-5 | 高频仍靠人 | 3 条/天、8 条/周仍手工，主探场景希望少重复劳动 |

### 4.2 运维

| # | 痛点 | 我们感受到的 |
|---|------|-------------|
| Y-1 | 状态不集中 | 运营一问「能不能查」，要逐个核实任务 |
| Y-2 | 失败发现晚 | 分区等问题常到使用时才暴露 |
| Y-3 | 协作成本高 | 「查不到数」报障信息不全，来回问 |
| Y-4 | 基础设施扰动 | 磁盘故障导致数据不可用，恢复顺序不清晰 |
| Y-5 | 变更心里没底 | 平台改表/停任务，我们不知道会影响哪些运营场景 |

### 4.3 优先级

```text
最急：O-2/O-3 + Y-1/Y-2  →  能不能查、查哪里、挂了早知道
其次：O-4/O-5 + Y-4      →  查得快、少手工、故障少折腾
再次：O-1 + Y-3/Y-5      →  统一入口、报障顺畅、变更可预期
```

## 5. 我们向平台方提出的诉求

> 以下均为**使用能力**，不限定实现方式。

### 5.1 运营诉求

| ID | 我们要什么 | 对应痛点 |
|----|-----------|---------|
| **U-O1** | **按业务场景查询**（如「主探过滤」「文件鉴定」），不用先选 Hive 表 | O-1, O-3 |
| **U-O2** | **一页看清 23 条场景是否可用**（昨日数据是否就绪、若不可用显示原因） | O-2 |
| **U-O3** | **每个场景标明数据来源/链路**（避免查错新旧表） | O-3 |
| **U-O4** | **统一时间选择**（近一月、单日等），不要每人改 SQL 占位符 | O-1 |
| **U-O5** | **查询进度与超时提示**（过久时提示缩小范围，而非一直转圈） | O-4 |
| **U-O6** | **结果导出**（常用明细/统计可导出，单次量级满足日常工作） | O-1 |
| **U-O7** | **高频场景一键跑**（至少：3 条多次/天的热度；二期：主探高频周任务） | O-5 |

### 5.2 运维诉求

| ID | 我们要什么 | 对应痛点 |
|----|-----------|---------|
| **U-Y1** | **一屏查看「影响运营的数据任务」是否成功**（与 19/23 条相关的日批/小时任务） | Y-1 |
| **U-Y2** | **失败主动通知运维**（不要用到晚上才知道分区有问题） | Y-2 |
| **U-Y3** | **运营报障模板**（场景、日期、是否已看就绪状态） | Y-3 |
| **U-Y4** | **磁盘等重大故障时：告知运营「哪些场景暂停、预计何时可查」** | Y-4 |
| **U-Y5** | **变更影响清单**：改表/停任务前，列出受影响的运营场景编号 | Y-5 |

### 5.3 共同诉求

| ID | 我们要什么 |
|----|-----------|
| **U-J1** | **书面《场景—数据—就绪时间》对照表**（23 条 + 就绪时点），双方确认 |
| **U-J2** | **查不到数时的自助说明**（先自查就绪状态，再转运维） |

## 6. 验收指标（使用方只验这些）

> 指标由**使用方体验**度量；建设方自选手段达标。  
> 带「基线待建」的项：能力上线后首月统计现状，再确认二期目标是否合理。

### 6.1 数据就绪（我们最关心「几点能开工」）

| 指标 | 含义 | 目标 |
|------|------|------|
| **D-1** | 昨日**审计/统计类**数据可供运营查询 | 每自然日 **09:00 前**可用（覆盖 19 条诉求） |
| **D-2** | 昨日**审计/统计类**数据就绪时点 | **01:00 前**完成产出（供早班提前使用） |
| **D-3** | 昨日 **IP/域名热度** 数据就绪 | 每自然日 **09:00 前**可用（#17、#18） |
| **D-4** | 日批失败日 | 运营侧 **09:00 前**看到「不可用」提示（19 条相关场景 **100%** 标出） |
| **D-5** | 月级数据可用率 | 审计/统计类：**≥99%** 自然日可用（基线待建） |

### 6.2 查询性能（运营体感）

| 指标 | 场景 | P50 | P95 | 备注 |
|------|------|-----|-----|------|
| **P-1** | 近一月明细类（19 条中的主体） | ≤5 分钟 | ≤15 分钟（二期 ≤10 分钟） | 运营日常最频繁 |
| **P-2** | 单日明细（如鉴定任务状态） | ≤1 分钟 | ≤3 分钟（二期 ≤2 分钟） | #1 |
| **P-3** | 热度类（#16–#18） | ≤3 分钟 | ≤8 分钟 | 多次/天 |
| **P-4** | 聚合统计（处理量等） | ≤2 分钟 | ≤5 分钟 | #20、#21 |
| **P-5** | 导出 ≤10 万行 | — | ≤60 秒 | 不阻塞其他人查询 |
| **P-6** | 同时查询 | — | — | 运营 **≥3 人**可同时查互不拖死 |

**使用方说明：** 若某次查询超过 P95，平台应给出**可读原因或建议**（如缩小日期、数据未就绪），而不是无反馈等待。

### 6.3 可用性与协作

| 指标 | 含义 | 目标 |
|------|------|------|
| **A-1** | 场景覆盖 | 一期 **≥19/23** 可在统一入口完成；二期 **23/23** |
| **A-2** | 手工查询占比 | 现 **78%** → 一期 **≤55%** → 二期 **≤22%** |
| **A-3** | 单次查询步骤 | 一期 **≤6 步** → 二期 **≤4 步**（从选场景到看到结果） |
| **A-4** | 查错数据导致空跑 | 较上线首月 **降 50%**（一期）→ **降 80%**（二期） |
| **A-5** | 运维接到报障时信息完整 | 一期 **≥90%** → 二期 **100%**（含场景、日期、就绪状态） |
| **A-6** | 故障通知运维 | 影响日批的失败 **≤15 分钟**内触达值班 |
| **A-7** | 高频场景「一键/自动」 | 3 条多次/天（一期）→ 累计 **≥8** 条多次/天+周（二期） |

### 6.4 一期 / 二期过关（使用方签字）

**一期（先能稳定用）：**

| 过关项 | 标准 |
|--------|------|
| G1 | D-1、D-4 达标；A-1 ≥19/23 |
| G2 | P-1、P-2 达标（抽测各 10 次） |
| G3 | U-J1 对照表双方确认；U-O2 就绪状态可见 |
| G4 | A-6 达标 |

**二期（好用、少手工）：**

| 过关项 | 标准 |
|--------|------|
| G5 | A-1=23/23；P-1 P95≤10min |
| G6 | D-5、A-2≤22%、A-7≥8 条 |
| G7 | U-O7 高频场景落地 |

## 7. 分期期望（我们要到的能力，不是交付件清单）

| 阶段 | 运营应感受到 | 运维应感受到 |
|------|-------------|-------------|
| **一期** | 19 个场景能在一个入口查；昨天数据能不能查一眼知道；查错表的次数明显下降 | 相关任务成功失败一屏看；失败有通知；报障有模板 |
| **二期** | 23 个场景全覆盖；热度/主探高频少手工；查询更快 | 月可用率可统计；变更有影响清单；大故障有运营通知话术 |

## 8. 需要平台方澄清的事项

以下影响我们能不能按上面指标验收，请建设方书面回复：

| # | 问题 | 关系 |
|---|------|------|
| 1 | 过渡期每个场景（23 条）**官方认定查哪类数据**？ | O-3、A-4 |
| 2 | 日批失败或磁盘故障时，**谁、以什么渠道**通知运营暂停哪些场景？ | D-4、U-Y4 |
| 3 | 近一月查询的性能承诺是否以**限定日期范围**为前提？最大可查多少天？ | P-1 |
| 4 | URL、IP 缺口场景在过渡期**官方查法**是什么？ | 避免我们自行摸索 |
| 5 | 一期统一入口**上线时间与试点范围**（谁先迁、谁后迁）？ | 运营排期 |
