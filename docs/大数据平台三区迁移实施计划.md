# 大数据平台三区迁移实施计划

日期：2026-09-10  
状态：执行计划草案，任务去留、责任人、目标表和排期等待项目组确认。  
目标：完成我方依赖大数据平台的生产和消费任务从Hive到StarRocks的适配、验证和切换；数据湖部门负责平台维护与原始数据接入。

## 1. 范围与依据

用户最新确认：数据湖部门已先迁audit、后迁stat原始数据到StarRocks；当前没有压缩表和中间表；三区部分MongoDB尚未具备；部分中间结果是否需要由业务方确认。

最新45项任务分类及责任边界见[Hive到StarRocks任务分类与迁移边界](Hive到StarRocks任务分类与迁移边界.md)。本计划中“补齐数据库、资源、接入”等前置工作由对应建设方负责，我方提出依赖要求并验证。平台全局下线由数据湖负责，我方仅确认本业务范围退出。

首批优先选择依赖齐备、确认保留且可隔离验证的消费者，audit和stat均可独立试点；必要中间表、SODL、Mongo接入及其他数据域并行准备，按各自依赖放行，不固定等到审计批次完成。混合读取任务必须落实全部必要输入的可用方案。

依据为两份原始任务CSV、`log/`加工说明和本次用户确认。清单记录不等于现网状态；实际SQL、任务版本和调度需在执行前复核。“SODL新链路”不等于“已进入三区的新平台”。新引擎已明确为StarRocks，版本、准确表名和接入机制由数据湖提供。

本计划细化当前三区实施安排。早期《YARN任务迁移顺序》和流程图用于参考血缘，不作为必须串行等待所有数据和数据库就绪的排期。

最新逐阶段交付、放行条件、三条实际链路推演、批量验证及切流操作单见[端到端迁移执行推演](端到端迁移执行推演.md)。以其中G0-G5关口细化本计划；验证从准备阶段开始，目标写入和实际业务读取均需验收。

## 2. 迁移原则

按最新[三类职责汇总](迁移任务三类职责汇总.md)划分承接：平台数据接入6项、平台内数据加工2项可与数据湖协商移交；业务消费与同步23项是我方重点评估范围，其中yara-sample-query-job和sp-old-update-report-cron-job已由用户确认通过SQL查询Hive，暂按业务消费归类，输出职责待补；其余14项单列为旁路、平台维护或退役，仍需核定迁移方式。数量为清单归类，不代表全部需要迁移。

- 先确认输入输出和业务用途，再决定改造范围。
- 优先尝试仅改连接、表名或字段映射；对批量验证失败的任务按原因改造。
- 压缩物理表取消后，必要的过滤、解析、关联和聚合语义仍需保留；不要求原样重建所有旧表。
- 分别验收中间表生产结果和消费同步结果，二者不能互相替代。
- 每条业务分支按自身依赖推进，Mongo缺失不阻塞无此依赖的任务。
- 旧数据生产链路是否仍被新区依赖必须单独确认，消费者改源不等于旧平台可停。

## 4. 先后迁移批次

### 第0批：并行准备和范围确认

同时开展表映射、任务去留、SQL收集、数据库及资源准备。按“审计直接消费、统计、旧DWB消费、混合来源、独立数据域”归类。未确认的任务保留在待定清单，不直接判定可下线。

退出条件：首批任务具有准确输入、运行版本、对照窗口、技术负责人和业务验收人。

### 第1批：审计只读验证

选取一个纯审计查询和一个代表性复杂查询，先完成新旧同窗口试跑及结果对比，再扩展至材料中的14个审计类场景。14个场景是候选集合，仍需逐条确认是否额外依赖维表或其他数据。

执行顺序：连接和表预检 → 参数化改源 → 固定分区限并发对跑 → 差异分类 → 修复重跑。结果分为直接通过、映射调整、逻辑改造、依赖阻塞、业务退役。

退出条件：选定范围的数据与查询结果通过，耗时符合双方确认目标。仅完成查询验证的任务不计为生产迁移完成。

## 5. 两类数据校验

### 5.1 生产的中间表是否正确

校验对象为“同一批原始数据和维表 → 加工结果”。固定输入窗口、截止点、维表版本和SQL版本；新旧对账之外，还要有按业务规则独立确定预期结果的样例。

| 项目 | 校验内容 |
|---|---|
| 完整性 | 应有分区、按日/小时/业务来源计数，缺失和迟到情况 |
| 内容 | 业务键、重复次数、字段值、类型、空值及双向差异 |
| 规则 | 过滤、JSON展开、URL标准化、域名匹配、未命中维表、聚合口径 |
| 指标 | 命中次数、设备数等消费者实际使用的指标 |
| 发布与恢复 | 完整数据才标就绪；重跑、补数和失败恢复不产生错误重复或部分可见结果 |

数据量大时先按分区和业务维度汇总定位，再查差异明细；不能把抽样通过描述为全量一致。粒度变化时按确认后的业务粒度比较。

### 5.2 消费到MongoDB、Redis、Kafka的数据是否正确

验证链路：平台查询结果 → 按业务规则推导的应写入结果 → 消费程序写入 → 目标端实际读回比较。平台记录数不一定等于目标记录数，需要考虑聚合、过滤、覆盖和删除规则。

| 目标 | 测试方式 | 检查项 |
|---|---|---|
| MongoDB | 准备已知初始状态的影子Collection，运行真实程序，再按业务键查询文档 | 漏写、多写、重复、字段与类型、upsert/更新/删除、部分写入失败后的恢复 |
| Redis | 使用影子前缀或测试实例，运行程序后读取实际Key及对应结构 | Key映射、值、类型、Hash/Set/ZSet内容、覆盖/删除、TTL；TTL按观察时点设置容差 |
| Kafka | 写入影子Topic，用独立验证消费者读取指定批次消息 | 消息ID/业务键、Key、Payload、Schema、缺失与重复；按业务要求验证同键/分区顺序 |

例：查询得到域名a.com设备数10，按规则应更新Mongo文档的devnum为10，或Redis对应值为10；读回若不存在即漏写，若仍为8即未更新。该例仅解释方法，真实集合、字段、Key和更新规则以任务代码为准。

每类测试覆盖正常、空结果、重复执行、部分失败重试和补数。重跑是否应覆盖、累加或允许重复投递，由业务契约规定。Kafka发布校验通过不等于后续所有消费者正确，若验收目标包含下游业务效果，还需继续验证实际消费结果。

缺Mongo等环境时记录“目标端校验阻塞”。生产表通过、查询通过、目标读回通过分别记账。报告至少记录任务ID、批次、输入版本、预期、实际、差异、覆盖范围、耗时、责任人和结论。

## 8. 单任务切流与回滚

1. 固定发布版本、切换时间/批次边界、目标配置、验收证据和回滚负责人。
2. 确认旧任务可恢复，保存检查点/消费位点及必要目标备份，完成切换前基线记录。
3. 双跑阶段新任务写影子目标；正式切换时控制写入所有权，防止新旧程序同时覆盖生产目标。
4. 对切换边界前后数据读回对账，检查延迟、错误和业务指标。只读查询可分使用方切入口；写任务按批次/分区或其他明确边界切换。
5. 异常时先阻止新任务继续产生错误，再按已演练方案恢复旧配置与处理位置，补齐边界数据。
6. 回滚不能只改连接：Mongo/Redis需处理已写错的状态；Kafka已发布的消息无法靠回切撤销，需预定去重、重放或补偿方式。

## 9. 旧压缩链路退出

停止一个消费者后，不得直接停止共享的整个`log_compress`。必须汇总检查：

- audit和stats的所有保留消费者已切换或批准退役；
- 三张旧DWB的必要业务语义已替代，各消费者完成验收；
- 新平台不再通过旧压缩任务生产或同步必要数据；
- 代码、调度、查询审计和业务方确认没有遗漏依赖，包括低频任务；
- 若拆除单个子任务，已调整Oozie fork/join和合并逻辑，避免影响其他仍保留分支。

满足条件后逐项停止旧调度并继续观察。历史表和数据按确认的保留期归档，最后办理删除；列入退役清单本身不是立即删除依据。

## 10. 任务跟踪模板

| 任务 | 批次/去留 | 技术/业务负责人 | 输入及目标映射 | 阻塞项及日期 | 生产校验 | 消费转换校验 | 目标读回 | 切流/回滚 | 退出状态 |
|---|---|---|---|---|---|---|---|---|---|
| 待填 | 待确认 | 待指定 | 待核对 | 待填写 | 未验证/不适用 | 未验证 | 未验证/不适用 | 待排期 | 未退出 |

周会按“依赖就绪、校验通过、已切流、可退出”分别汇报任务数。将缺口、下一步动作、具体责任人和预计解除日期同步维护到困难点台账，不使用部署成功代替迁移完成。
