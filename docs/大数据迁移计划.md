# 大数据迁移计划（三阶段）

更新日期：2026-09-16。依据：用户提供的三阶段安排，作为当前计划组织方式；此前详细执行清单保留作检查项参考。本文不沿用旧版25个工作日完成切换的估算作为新计划承诺。

时间口径：准备阶段d暂按工作日理解，业务观察7d按自然日理解；实际开工日、负责人及资源投入待落实。执行阶段暂定10人天（DEC-006），最终下线工期待确认；试点后复核工作量及日历排期。

## 1. 前期准备

### 1.1 任务对齐梳理——3d

- [ ] 整理迁移与下线任务，核对45项盘点对象的实际运行情况、业务用途和读取方。
- [ ] 区分保留迁移、退役、旁路/无需本次改造及待确认。7项退出相关标记不全是已完成下线，剩余38项也不等于全部需要改造。
- [ ] 梳理所需迁移表：原始日志、基础表、维表和必要中间结果，落实生产者及消费者。
- [ ] 确认业务负责人、任务负责人、验收人、重要性、结果口径及处理时效。
- [ ] 落实两张已决定下线表对ctig、attack-ip、black-ti及DataX相关分支的影响。

检验结果：任务去留清单、表依赖清单、首批候选及业务验收标准；未决项有负责人和期限，不能默认下线。

### 1.2 协助数据湖搭建公共数据接入、加工与维护——3d

- [ ] 测试环境构建所需迁移表的数据——1d：确认目标表、字段映射、样例和更新规则，构建首批可用输入。与1.3的数据收集使用同一套样本，避免重复建设。
- [ ] 中间表链路逻辑说明——2d：说明输入、关联、过滤、去重、聚合、输出粒度及发布时机，明确必要逻辑和取消逻辑，由数据湖与任务方确认承接边界。
- [ ] 将实际接入开发、加工实现、历史回填和数据验收另列交付日期及负责人。

检验结果：测试表及初始数据可访问，中间加工说明和责任边界确认，生产交付有明确安排。

注意：上述3d是协助构建数据及说明链路的安排，不等于数据湖全部生产接入、加工和历史回填已完成；未完成的交付会阻塞依赖它的业务批次。

### 1.3 链路搭建与验证数据准备——各子项合计7.5d

| 子项 | 预计时间 | 要做的事情 | 检验结果 |
|---|---:|---|---|
| 生产环境链路打通 | 0.5d | 网络、账号、权限、连接与目标可达性检查 | 生产通路连通记录；不等于已切流 |
| 三区Mongo表新建及同步 | 1d | 找春兰对齐数据格式、新增同步范围，确认集群/库/集合、业务键、字段、索引和更新删除规则。目前三区还缺5个表，需要结合迁三区进行同步 | 目标可用、样例及同步检查通过；大规模回填另估工期 |
| 测试环境搭建验证通路 | 2d | 输入→必要加工→真实任务→隔离Mongo/Redis/Kafka或其他输出→业务读取 | E2E冒烟通过，目标可重置、可读回，不影响生产 |
| 数据收集及测试集构建 | 3d | 从获准生产数据中收集表内样本、旧结果及必要日志，构造正常和异常场景 | 同批数据结果是否相同 |
| 现存数据每日生产情况统计 | 1d | 建立旧任务产量、耗时、延迟、业务键覆盖和错误情况的基线 | 逐任务基线报表和统计方式，后续按日持续采集 |

- [ ] 测试集覆盖新增、更新、删除、空结果、迟到、重试、补数和部分失败。
- [ ] 合成日志与真实生产样本分别标记；合成数据用于已知预期验证，真实快照用于同窗口对账。
- [ ] 生产样本收集与测试通路搭建可并行；目标读回验证必须等目标和输入就绪。
- [ ] “每日生产情况统计1d”指基线工具/报表建立及已有历史统计，不代表一天就覆盖完整周周期。

### 1.4 前期准备完成关口

- [ ] 首批任务已确认保留、依赖和验收人，所需输入实际交付并校验。
- [ ] 测试环境能跑通真实业务链路，具备可比测试集、旧结果和输出读回能力。
- [ ] 后续批次的数据湖交付与必要中间加工有具体负责人、日期和验收方法。

前期准备各项若完全串行，为3＋3＋0.5＋1＋2＋3＋1＝13.5个工作日。允许依赖就绪的工作并行，实际历时需结合人员容量排定；13.5d不是已经确认的人日投入或项目总工期。

## 2. 执行阶段——暂定10人天

2026-09-16用户确认先按10人天安排执行阶段。按本章节范围计入首批试点、各批迁移改造、效果验证、问题修复及切换操作；前期准备、执行后的7个自然日观察和老任务下线另列，不并入这10人天。各子项分配试点后细化，不重复计算试点任务。

10人天是参与执行人员的合计工作量，不是固定10个工作日。1人全职有效投入约需10个工作日；2人完全可并行的理想工作量折算为5个工作日，实际还受中间结果依赖、验证运行时间、数据交付和切换窗口影响，不能直接承诺5天完成。

该数值为暂定预算，尚未经试点实测；如范围或实测工作量变化，应追加调整依据，不以预算限制省略验收或必要改造。

### 2.1 迁移顺序

业务执行顺序：首批试点 → 热度/统计库 → 误漏报治理 → 情报生产 → 运营展示。此处为业务批次优先顺序，实际验收仍须满足上游数据和加工依赖；准备工作可提前并行。

#### 2.1.1 首批试点任务——工期待试点范围确认

首选候选：若SODL先就绪，可选择`ip-security-log-etl-prc`或`domain-security-log-etl-prc`。两者均读取`sodl.network_security_log`，分别输出Redis和Mongo。先验证一个，再复用输入和工具推进另一个。

- [ ] 从候选中选择依赖已齐备、业务影响可控的任务，不把候选名单视为切换批准。
- [ ] 完成字段/方言适配、固定窗口对账、目标读回、业务用例及性能验证。
- [ ] 测试切换边界与恢复能力，业务放行后切换并开始观察。
- [ ] 记录实际工作量、差异定位时间和性能，估算后续批次工期。

试点任务归属情报生产类，后续该类别统计时只计一次，不重复迁移。

#### 2.1.2 先迁移热度库任务——5项盘点对象

此处沿用此前“热度、活跃度与统计库生产”分类，不是5项全部只做热度统计。

| 任务 | 业务内容 | 前置注意事项 |
|---|---|---|
| `topthreat_hot_stat` | 文件、URL、域名统计 | 核实全部日志及混合来源分支 |
| `top-visit-host-produce-job` | 访问TOP库、过滤包支撑 | 输入日志、辅助数据与Redis目标就绪 |
| `filter-layout-ip-seg-stat-prc` | IP网段统计 | 审计压缩输入替换、IP信誉依赖及性能验证 |
| `domain-heat-stats-cron-job` | 域名热度库 | 原材料去留待确认；必要中间结果先就绪 |
| `black-ti-context-produce-prc` | 恶意IOC活跃统计 | 所需DWB先验收；租户表潜在依赖仍需核实 |

- [ ] 对确认保留的任务实施迁移；不把“5项安排”当作所有去留均已确认。
- [ ] 先验输入和必要中间结果，再验消费及实际业务使用。
- [ ] 压缩改原始分支做规模性能验证，不能仅改表名。

#### 2.1.3 迁移误漏报任务——3项待逐一核定

- [ ] `ati-pdns-cache-job`：核实过滤目的及业务归属，验证Mongo和Redis两端状态。
- [ ] `domain-hit-devnum-cronjob`：验证命中设备数及实际降误报使用场景。
- [ ] `black-file-clean-cronjob`：原材料去留待确认；保留时验证白文件列表及文件云接收效果。

`phishing-url-operation-prc`已确认下线（DEC-004），不在本批迁移名单中。

#### 2.1.4 迁移情报生产任务

- [ ] 按[业务分类](./迁移任务按业务领域分类.md)中12项情报生产、研判与分发任务核定保留及是否涉及本次改造，扣除已完成试点项，不重复计数。
- [ ] 处理攻击IP、域名/IP鉴定、回扫、检测输入和分发链路的完整输入与目标输出。
- [ ] `attack-ip-analysis-cronjob`落实skyeye IP表退出后的规则调整，按调整后的业务标准验收。
- [ ] 旁路或无需本次平台改造任务核实边界，不强行做换源迁移。

#### 2.1.5 运营展示最后迁移

- [ ] 核定`online-dev-warehousing-prc`、`cloud-display-manager-prc`、`dashboard-stats-job`、`cipd-product-resource-monitor-prc`、`svd-activity-stat-job`的迁移范围和去留。
- [ ] 校验在线设备、看板数据、监控指标、更新周期及展示结果。
- [ ] `thug-task-monitor-prc`有历史已下线记录，核实停用状态，不恢复迁移。

“运营展示最后迁移”指业务任务切换顺序。迁移所需运行监控、旧数据基线和告警从准备阶段开始，不推迟到最后。

#### 2.1.6 需要补齐批次归属的业务

本轮顺序尚未单列“报告、样本查询与对外上报”5项：`ctig-report-data-analysis-prc`、`yara-sample-query-job`、两个`cert-app-samplesync*`任务、`sp-old-update-report-cron-job`。需在前期梳理时确认去留、交付时限及插入哪个批次，不能遗漏，也不擅自安排到运营展示之后。

公共接入和必要加工按受影响业务批次先行交付；维护类单独核定替代或退出，不能因编入“前期协助”而视为实际全部完成。资产漏洞类和用途不明历史任务按退出清单处理。

### 2.2 执行时效果验证——每批都做

- [ ] 配合业务监控生成数据，在同一完整窗口、输入版本与目标初始状态下对比旧结果。
- [ ] 输入检查：完整性、字段、业务键、历史覆盖及增量时效。
- [ ] 中间结果检查：过滤、关联、去重、聚合和完整发布。
- [ ] 消费检查：业务对象、关键字段、统计值、缺失和重复。
- [ ] Mongo检查文档及更新删除；Redis检查Key、类型、值、TTL与旧Key清理；Kafka检查消息及真实消费效果。
- [ ] 文件、指标和接口按实际接收及使用验证，不能只验证上述三类存储。
- [ ] 对比每日产量、运行耗时和延迟；行数一致不能单独证明正确。
- [ ] 已批准取消的表/分支导致的预期差异单独记录，由业务确认新的验收标准。
- [ ] 完成正常、峰值、重试、补数和恢复验证；关键差异解释闭环后才允许切换。

每批产出：任务清单、版本、差异报告、性能结果、目标读回、业务验收、恢复演练及切换记录。切换时明确批次/位点和迟到归属，同范围单一有效生产写者。异常停新写，恢复/补偿数据，再恢复旧任务与读取并补边界对账。

## 3. 执行后 -- 2d

### 3.1 业务观测持续7d

- [ ] 每批从自身切换日起观察至少7个自然日，最终收口以最后一批通过为准。
- [ ] 观察产量、时效、业务读取、重试、补数、资源和告警情况。
- [ ] 低频业务覆盖约定实际周期或业务认可的等价演练；不足时延长，不能仅以7天无告警通过。
- [ ] 业务验收人签署观察结论，关键问题闭环。

### 3.2 老任务下线——工期待确认

- [ ] 停止获批旧实例和调度；保留必要恢复版本、旧输入及数据保留期安排。
- [ ] 检查共享旧接入、中间加工、Hive查询和中转供数；全部保留消费者退出后再停止共享上游。
- [ ] 核实历史已下线任务，完成新增退役项的执行记录和输出影响处理。
- [ ] 完成监控、告警、故障处置及负责人交接。

检验结果：业务观察签字、旧依赖退出报告、停调度记录及运行交接。停止任务不等于立即删除数据；我方退出不等于全平台已下线。

## 4. 阶段检查节点

以下是本三阶段计划的检查节点

| 节点 | 必须拿到的检验结果 |
|---|---|
| 准备完成 | 首批范围明确、输入验收通过、生产连通与测试E2E通路具备、可复现测试集和生产基线齐备 |
| 试点完成 | 查询、目标读回、业务用例、性能及恢复能力通过，形成后续实测排期 |
| 每个业务批次完成 | 保留任务及分支全部覆盖，每项质量验收和切换有证据；试点不重复计完成 |
| 执行阶段完成 | 所有确认保留迁移项已切换；报告/样本/上报等未单列业务也有处置结论，不遗漏 |
| 项目收口 | 最后一批观察通过、旧依赖退出、退役项完成、交接签字 |
