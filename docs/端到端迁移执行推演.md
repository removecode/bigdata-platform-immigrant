# Hive到StarRocks端到端迁移执行推演

日期：2026-09-10。
状态：执行方案，尚未完成现网验证；负责人、验收阈值、承接关系及日期须由项目组确认。

## 1. 目标与边界

目标是保持业务数据口径、时效和服务连续性，在可验证、可停止、可恢复的前提下完成迁移。不能承诺零风险；用隔离验证、明确放行条件、单写者切换和补偿演练控制风险。

沿用45项全量盘点：平台接入6项、平台内加工2项、业务消费与同步23项，其余14项单独核定迁移方式。23项消费暂分原始日志7项、压缩日志3项、中间表7项、其他业务表/维表4项、输入层级待确认2项。分类不等于全部需要改造或全部已确认保留。

数据湖已按audit先、stat后的顺序迁入原始数据，但字段、历史范围、完整数据截止点、可用性仍需验收。SODL日志、Mongo接入数据及必要中间结果不默认已经交付。数据湖维护平台；接入与中间加工是否交给数据湖，逐项确认，不能视为已经承接。

本方案细化[实施计划](大数据平台三区迁移实施计划.md)。批次是依赖分组，不是必须串行执行的阶段。原始表、压缩表和中间表消费者按各自条件并行推进。

## 2. 从业务结果倒推工作

每条链路先填清楚：谁用结果、允许多久不更新、错数据有什么后果、输入来自哪里、结果由谁写、实际读取者何时切换、出错如何恢复。

| 阶段 | 执行动作 | 必须产出 | 放行条件 |
|---|---|---|---|
| G0 范围确认 | 用代码、调度、查询记录核对45项；拆SQL/子任务；业务决定保留、替代、退役 | 任务台账、业务验收人、输入输出和风险级别 | 首批任务已确认保留，SQL版本及实际用途明确 |
| G1 输入就绪 | 与数据湖核对原始日志、Mongo基础数据、必要模型；验证读权限和完整窗口 | 表级数据契约、映射与输入验收报告 | 相关输入可比、可访问、历史与时效达标 |
| G2 改造与查询验证 | 最小适配连接、表字段、方言；同窗口跑新旧查询 | 版本化SQL、差异报告、性能报告 | 关键字段及业务指标满足预先约定标准，差异有结论 |
| G3 端到端影子验证 | 真实程序写隔离目标，读回并验证业务读取；演练重试、补数和回退 | 目标读回、业务用例、故障恢复证据 | 全链路通过，性能满足约定，恢复方案可执行 |
| G4 切流 | 发布已验证版本，固定边界和写入所有权，逐批切换生产者及相关读取者 | 切流记录、边界对账、监控与负责人 | 无未解释关键差异，业务及技术负责人同意 |
| G5 观察与退出 | 覆盖业务周期持续对账，核对旧链路残留依赖 | 业务签字、旧调度停用和保留期记录 | 观察达标，无保留消费者依赖旧链路，满足退出审批 |

只有G5完成才计业务迁移闭环。部署成功、SQL成功、影子数据正确、生产切流成功分别统计，不能互相替代。目标环境缺失时可推进G2，不能将G3标为通过。

## 3. 前期准备：并行启动四条工作线

### 3.1 任务和业务线

逐任务确认技术负责人和业务验收人；历史负责人只作联系线索。收集部署代码/SQL版本、调度周期、参数、最长历史回看窗口、补数方式、运行时长和最近成功记录。

业务明确：保留哪些结果字段、过滤和聚合口径、业务键、覆盖/累加/删除语义、时效目标、允许差异、错漏数据影响。可下线必须书面确认；未确认不能默认停止。月报、低频任务和人工触发任务单独核实。

中间表按消费者用途确认，不按整张表一刀切：有保留消费者的必要逻辑必须有替代；无用途模型不自动重建。yara-sample-query-job、sp-old-update-report-cron-job优先补实际SQL、表名和输出。

### 3.2 数据湖对齐线

对齐单位是“每张输入表/数据集”，不是笼统询问“数据是否迁好了”。共同维护以下交付单：

| 数据范围 | 需要数据湖/承接方回答 | 我方验收 |
|---|---|---|
| audit/stat | 目标表、字段与类型、事件时间/入库时间、时区、选数过滤、去重、历史范围、迟到与补数 | 新旧同完整窗口按业务维度和字段对账；压缩表旧口径单独映射 |
| SODL六张日志 | 是否提供dns、endpoint_security、http、network_security、sip_iocstat、url日志；由谁接入 | 比较接入范围和过滤规则；不能把audit/stat交付当作SODL交付 |
| Mongo接入数据 | hashinfo全量/增量及DataX实际作业清单，源库/集合与目标表，初始快照和增量衔接 | 业务键、字段类型、更新/删除、重放幂等及延迟；DataX目录不能代替准确表名 |
| 其他维表/业务表 | 信誉、设备、上传、标签、ioc_vertex、business_data等的生产者和目标 | 按实际消费者逐项核实，不默认全部由DataX生产 |
| 必要DWB结果 | 是否保留，谁实现，模型粒度与加工规则，何时发布完整结果 | 固定输入及维表版本，对账中间结果，再验证下游 |
| 平台服务 | StarRocks版本、连接/认证、查询/导入方式、资源组、限额、超时、维护及故障联系 | 用真实SQL和任务执行器测试，而非只验证端口连通 |

每张表还要有交付负责人、承诺日期、完整数据截止点、保留期、就绪信号、变更通知和故障补数责任。“已建表”“已有数据”均不等于输入验收通过。

Mongo向新平台的同步可由数据湖另建链路，不要求照搬旧任务；但双方必须明确旧接入任务何时能停。新链路若仍依赖旧Hive中转，记录为过渡依赖，不算平台完全退出。

### 3.3 环境和资源线

逐任务列出执行环境到StarRocks、源Mongo、输出Mongo/Redis/Kafka、Prometheus、HDFS/SCP及其他外部系统的连接方向、最小权限、容量、限流和负责人。三区Mongo缺失只阻塞对应任务，不阻塞无关查询验证。

同时申请生产与影子环境。影子Mongo使用独立集合/库及正确索引；Redis优先隔离实例，若用前缀需确保所有Key路径、脚本和清理逻辑均隔离；Kafka使用影子Topic并确认不会触发生产消费者；Prometheus及外部API使用隔离目标，关闭实际业务副作用。

资源预算包含新旧双跑、对账扫描、影子存储、导入、补数及峰值并发。先单任务测量再增加并发，约定资源/延迟超限后的暂停条件。未经批准不执行全量无界扫描或高压故障测试。

### 3.4 验证准备线

前期必须交付“具备本批E2E验收能力的测试环境”，而非仅提供数据库连接。范围包括可比输入及维表、必要中间加工、真实任务运行、隔离目标、实际业务读取、日志/指标/差异报告；目标初始状态可准备和重置，支持重试、补数及恢复演练。按权限使用脱敏数据，隔离全部写入和外部业务副作用。以本批完整路径冒烟报告作为M1环境交付证据；正式结果验收仍在M2进行。模拟服务可辅助开发，不能代替最终真实集成验收；测试环境通过也不能代替生产规模验证。

先制作验证用例和对账配置，再批量修改SQL。对账窗口使用双方已确认完整的相同数据范围，不简单取“当前时间之前”；若源会更新，固定快照/版本或构造受控输入。

契约写清业务键、重复记录是否有意义、字段类型、空值、时间精度、大小写、集合/数组顺序及浮点容差。规范化不能掩盖业务差异。没有天然唯一键时按多重集合比较，不能用去重后的集合丢掉重复差异。

事先确定关键字段、漏写、多写、重复、延迟、耗时和资源阈值及批准人，不在看到差异后临时放宽。关键数据默认不接受未解释差异；允许差异须有业务依据。旧结果不是绝对正确，另备业务规则推导的预期样例。

## 4. 三条实际链路推演

### 4.1 压缩表改读原始表：filter-layout-ip-seg-stat-prc

现有输入为audit压缩表及IP信誉，输出Redis。顺序为：

1. 业务确认保留，取现网SQL、Key规则、更新方式及Redis读取者信息。
2. 数据湖交付audit新表映射，另行确认IP信誉来源和可用版本；复核旧压缩步骤的字段与过滤条件。
3. 保持统计口径，以最小SQL适配改读新原始表，固定窗口与信誉版本对比结果和性能。
4. 真实程序写影子Redis，从已知初始状态运行，验证Key、结构、数值、TTL、覆盖/删除和重复运行。
5. 通过实际业务读取路径核验。如果输出Redis实例也变化，协调读取者配置和缓存预热；写入新实例不代表业务已读到新结果。
6. 固定批次/键范围及写入所有权，切换后验证边界和业务指标；异常按已演练方案停止新写入并恢复正确状态。

audit已迁不代表这个任务立即可切：IP信誉、目标Redis、口径、性能和业务读取路径仍是前置。原始数据量增加也不必然导致StarRocks更慢，以实际窗口和并发测试为准。

### 4.2 SODL经中间表到业务：domain-heat-stats-cron-job

任务清单状态待确认，先由业务决定是否保留；未确认前可盘点，不承诺开发。

1. 若保留，核对实际需要的Domain中间结果及历史窗口。
2. 核对材料中的ClickHouse -> sodl_ods_info -> Hive SODL日志链路，确认新平台如何提供所需日志；sodl_ods_info_new的现网版本关系待核实。
3. 根据现网Domain加工SQL逐项补齐必要日志、信誉、标签、设备等依赖，不因存在六张SODL表就假定所有维表已就绪。
4. 业务、数据湖、开发决定复用等价结果、集中生产必要模型或内联所需加工逻辑；共享模型优先统一验证，避免多个消费者重复实现不同口径。
5. 固定输入验证Domain中间结果的粒度、过滤、关联、聚合及完整发布，再运行热度消费SQL。
6. 写影子Mongo，验证文档、更新删除、历史初始化与业务查询；完成切流演练后再切换。

这条链路的潜在关键路径是“日志与维表交付 -> 必要模型等价实现 -> 消费验证”，不是简单换连接。开发可提前进行SQL适配，正式验收不能跳过输入完整性。

### 4.3 Mongo基础数据接入：hashinfo及其消费者

材料明确sync-mongo2hive-job从Mongo产出sri.ods_sri_hashinfo及增量表；cert-app-samplesync-job还读取business_data并导出文件。

1. 数据湖/接入承接方确认源Mongo库、集合、业务键、全量与增量方案；business_data的生产者另查，不自动归给该任务。
2. 验证初始快照与增量位点衔接，覆盖快照期间更新/删除、重复重放、断点恢复；不能仅比较首批行数。
3. 对新平台hashinfo验证业务字段及查询时效，确认消费者究竟读当前状态还是历史快照，防止新旧维表时点不同造成伪差异。
4. business_data也就绪后，对比导出选数与文件内容、格式、条数和完整发布；国家版任务另验证SCP到达、接收处理及防重复。
5. 核对其他hashinfo消费者后，才能决定旧接入任务的退出时间，不能因为一个导出任务通过就停止共享接入。

## 5. 高效批量改造与验证

提效建设目标扩展为“批量自动化迁移”，当前为待建设能力，非已实现系统。以任务配置及依赖图驱动自动预检、模板化适配、测试部署、同窗口对账、目标读回、报告和发布包生成。按输入及中间结果就绪状态编排，下游不能绕过验收。复杂SQL/UDF和业务模型变更进入人工评审；审批后可以自动执行已验证批次的发布/切流，不能无人审批全量生产切换。

自动化须具备版本追溯、干运行、并发限制、检查点、失败暂停、幂等与恢复记录。故意注入缺依赖和错误结果，验证工具确实拦截失败；Kafka及外部接口等副作用按业务幂等/补偿契约处理，禁止盲目重试。代表任务通过后逐批扩大。M2交付工具试点证据、适用覆盖范围和需人工处理清单，不宣称所有任务均能自动改造。

批量单元是SQL/子任务，业务验收单元仍是完整任务。使用一份参数化配置记录：任务ID、SQL ID、代码版本、新旧连接/表映射、时间窗口、依赖快照、业务键、字段比较规则、影子目标、预期输出、超时和责任人。

| 步骤 | 批量动作 | 结果处理 |
|---|---|---|
| 预检 | 检查连接、表、字段、窗口、权限、目标隔离和依赖就绪 | 缺依赖标阻塞，不反复执行必失败查询 |
| 最小适配 | 修改连接/表名/字段及必要方言；先只读限范围试跑 | 分为直接通过、字段映射、SQL兼容、模型改造、依赖阻塞 |
| 查询对账 | 按相同窗口运行，先按业务维度定位，再做关键范围完整差异检查 | 输出漏项、多项、重复、字段及指标差异；抽样/哈希只能定位或辅助，不能冒充全量一致 |
| 程序验证 | 真实程序执行转换并写隔离目标 | 查询通过但写入失败单独定位，不混为数据湖问题 |
| 目标与业务验证 | 独立读回并运行业务读取用例 | 区分数据存储正确和实际业务消费正确 |
| 扩大覆盖 | 从小窗口到正常、峰值、迟到、空结果、跨日及补数窗口 | 达标才提高并发；周/月任务补对应周期或受控历史回放 |

共用连接适配、映射模板、结果比较和目标读回工具，业务特有规则仍逐任务配置。不做无差别字符串替换，不假定所有Hive函数在StarRocks中等价。

差异优先按“输入不齐/迟到 -> 维表时点 -> 字段或过滤 -> 方言/UDF -> 程序转换 -> 目标写入”定位。共享输入问题修一次、重跑所有受影响用例，避免每个消费者独立排查同一问题。

## 6. 验证不是最后一步：五层验收

| 层次 | 验证对象 | 关键证据 |
|---|---|---|
| 输入层 | 原始日志、Mongo接入表、维表 | 相同完整窗口、业务维度计数、主键/多重集合、类型、更新删除、延迟 |
| 加工层 | 必要中间结果 | 固定输入预期样例及新旧差异，JOIN基数、去重/聚合、完整发布、重跑恢复 |
| 查询转换层 | 消费SQL和程序转换 | 应选数据与应写结果；不能用查询条数直接代替目标条数 |
| 目标层 | Mongo/Redis/Kafka/文件等 | 从目标实际读回；覆盖新增、更新、删除、重复执行、部分失败、补数 |
| 业务层 | 真正读取这些结果的接口、报表、规则或消费者 | 业务查询命中、统计口径、时效及异常用例，由业务负责人确认 |

Mongo验证文档业务键、类型、索引相关行为、upsert与删除；Redis验证Key和结构、值、TTL及过期/旧Key清理；Kafka验证批次消息键、Payload、Schema、重复和业务要求的顺序，并验证相关下游处理。Kafka通常只能保证分区内顺序，不设未经确认的全局顺序要求。

状态型输出必须从相同或可解释的初始状态对比；增量任务写空影子库可能无法验证历史更新与删除。大数据量使用受控代表样本加生产规模只读验证，报告明确覆盖边界。影子环境共享生产资源时也要限制负载。

故障演练仅在隔离环境或批准的演练范围内进行，至少覆盖断连/部分写失败、进程中断恢复、重复批次、迟到补数和回退。每个失败场景都记录恢复后的数据状态，不只记录程序重新启动。

## 7. 切流当天操作单

1. 技术和业务负责人确认G1-G3证据、允许差异、数据时效、资源余量、监控阈值、停止条件、恢复时间目标和补偿负责人。冻结本批版本；非必要变更不合并发布。
2. 保存旧任务配置、发布版本、调度参数、成功批次/位点及按目标需要准备的备份。确认旧输入在回退观察期继续可用，避免只有旧代码、没有旧数据。
3. 若目标实例迁移，完成历史数据初始化、增量追平、索引/TTL/权限检查及业务读取者切换预案。不可直接假设历史数据能够全部重算。
4. 对日批固定不重叠时间边界，例如旧任务负责事件时间小于T、新任务负责大于等于T，并约定迟到修正归属；若按其他业务时间选数，使用其真实口径。流式按分区记录位点，不能简单把不同Topic的offset当作等价。
5. 等旧运行实例结束或受控停止，核实没有残留写者；通过调度互斥/所有权机制确保同一生产目标范围只有一个有效写者。目标读回失败或所有权不清时停止切换。
6. 启动新任务并监控首个完整批次，核对切换边界前后及迟到数据；按任务能力小批放量。无法按键/分区隔离写入的任务不得强行比例灰度，使用整批切换。
7. 相关业务读取者切换后再检查真实读取结果及业务指标，确认不是仍在读旧实例。技术与业务共同记录本批结论。

回退触发包括关键错漏/重复、数据延迟或性能超限、目标写入不可恢复、实际业务用例失败。阈值必须在切流前填实，不能临场决定。

回退顺序：暂停新写者 -> 确认错误写入范围和正确恢复点 -> 恢复/补偿目标状态 -> 恢复旧写者及必要读取路由 -> 重放边界数据 -> 对账确认。Mongo/Redis按任务语义选择备份恢复或确定性重建，不盲目覆盖无关业务更新；Kafka已被消费的消息不能靠回切撤销，必须具备下游去重/补偿方案，不具备则不放行相关切流。

## 8. 观察、退出与项目推动

观察期按业务周期与风险确认，可从连续7个日批周期提议，不作为固定通用门槛。周期较长的任务必须覆盖相应周期或认可的历史回放，并约定后续观察。观察期间持续看数据新鲜度、数量突变、关键业务指标、目标写入失败、资源及补数情况。

共享旧接入、log_compress和DWB任务只有在所有保留消费者已迁或批准退役、新平台不依赖其供数、低频及隐含消费者已核实后才能停止。先停调度观察，再按审批的保留期归档；不立即删除旧数据。业务迁移验收和旧平台全局退役分别记录，由不同责任方批准。

| 推动节奏 | 项目推动者关注内容 | 产出 |
|---|---|---|
| 启动前两个工作日（建议） | 每项负责人、首批候选、数据湖和业务待决问题、环境缺口 | 首批任务卡与决策清单；资料不足则明确阻塞，不承诺上线日期 |
| 启动首周（建议） | 输入交付验收、小规模SQL及影子链路试点、资源测量 | 可直接适配/需改造/被阻塞的真实比例，据此估工期 |
| 日常短会 | 只看阻塞、差异及当天决策，逐项落实下一动作、责任人和日期 | 更新任务状态与阻塞台账 |
| 每批切流前后 | 看验收证据、回退能力、业务窗口及实际结果 | 放行或拒绝放行记录，不以完成率替代风险评审 |
| 每周 | 数据湖交付、业务去留、跨团队资源、旧链路依赖 | 按G1/G2/G3/G4/G5分别汇报，调整批次和关键路径 |

首批建议从确认保留且依赖最少的任务选择：filter-layout-ip-seg-stat-prc可作audit到Redis候选，cipd-product-resource-monitor-prc可作stat分支候选，但须各自依赖就绪；topthreat_hot_stat的纯audit文件分支可先只读验证，不代表整个混合任务通过。SODL、Mongo同步及中间模型工作同步开展，不排到全部audit任务完成之后。

最容易拖慢项目的是数据交付和历史范围不清、维表/模型责任无人承接、业务去留迟迟不决、缺目标验证环境，以及差异无法复现。应优先消除这些不确定性，而不是先把所有SQL改完。

任务卡最少字段：任务/SQL ID、类别与输入标签、技术/业务负责人、保留决定、输入/输出/实际读取者、数据契约、依赖交付日期、验证窗口与规则、差异报告、性能、G1-G5状态、切流边界、回退补偿、旧依赖退出条件。
