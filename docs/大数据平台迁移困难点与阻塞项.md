# 大数据平台迁移困难点与阻塞项

**文档日期：** 2026-09-08  
**更新日期：** 2026-09-10  
**用途：** 记录大数据平台向三区迁移过程中的困难点、影响、责任角色和解除条件，作为项目周会、风险升级和切流评审的统一台账。  
**当前范围：** 数据湖部门已先迁audit、后迁stat原始数据到StarRocks，当前无压缩表和中间表；我方负责依赖平台的业务生产和消费任务迁移，不承担平台维护。

端到端风险、等待/人工/运行耗时分析及提效措施见[E2E迁移风险与提效分析](E2E迁移风险与提效分析.md)。本文B编号保留作原阻塞台账，E编号用于E2E分析，不表示已经发生事故。

**最新责任边界：** 平台接入、物理表设计和平台资源由数据湖/对应建设方负责；台账中的平台缺口是我方迁移依赖，不代表我方承建。最新任务分类、SQL快照差异及性能验证方案见[Hive到StarRocks任务分类与迁移边界](Hive到StarRocks任务分类与迁移边界.md)。历史“stats是否迁入”的待办调整为“stat交付字段、历史范围及可用性验收”。

---

## 1. 当前判断

当前项目不是单纯的 YARN 任务搬迁，而是同时涉及：

1. 三区基础设施和数据库能力补齐；
2. 旧压缩日志链路退出后的数据模型替代；
3. 中间表、任务和业务场景的保留/下线决策；
4. 新旧平台数据验证、业务验收、切流与回滚；
5. 计算、存储、网络和人员资源协调。

在以下事项闭环前，不建议承诺旧链路下线时间：

- 三区 MongoDB 等依赖是否具备；
- 两张压缩日志表及三张旧 DWB 表的替代关系；
- 下游消费者是否全部识别；
- 新旧数据对账和业务验收是否通过；
- 迁移所需资源是否完成测算和分配。

## 3. 重点困难说明

### 3.1 三区数据库及 MongoDB

部分任务虽然计算可以迁入三区，但结果需要写入 MongoDB、Redis、Kafka 或 Prometheus。若三区缺少 MongoDB，不能把“任务已部署”视为“业务已迁移”。

需要逐项确认：

- 三区是否新建 MongoDB，还是允许访问原区域 MongoDB；
- 数据库版本、规格、副本、存储、备份和容灾要求；
- 账号、认证、网络策略和域名切换方式；
- 双跑期间是否使用影子库/Collection；
- 数据同步、最终切换和失败回滚方式；
- 跨区访问是否符合安全与时延要求。

当前明确涉及外部输出的任务包括：

- `phishing-url-operation-prc`：输出 MongoDB，当前待确认；
- `domain-hit-devnum-cronjob`：输出 MongoDB；
- `active-domain-elt-job`：输出 Redis；
- `black-ti-context-produce-prc`：输出 MongoDB、Redis；
- `filter-layout-ip-seg-stat-prc`：输出 Redis；
- `cipd-product-resource-monitor-prc`：输出 Prometheus 指标。

### 3.2 中间表去留确认

中间表不能只依据“近期没人反馈”决定删除。建议对每张表执行四步确认：

1. 扫描代码仓库中的 SQL 引用；
2. 扫描调度平台近 30～90 天运行记录；
3. 扫描 Hive/查询引擎审计日志中的实际访问；
4. 由业务负责人确认保留、替代或下线。

当前重点表：

| 类型 | 表 |
|------|----|
| 压缩日志表 | `csc.ods_csc_log_audit`、`csc.ods_csc_log_stats` |
| 审计派生旧 DWB | `default.dwb_md5_info`、`default.dwb_url_info`、`default.dwb_domain_info` |

若决定不保留旧表，应明确其业务语义由新平台哪张表、视图或主题模型承接，而不是只做物理删除。

### 3.3 迁移资源

资源评估至少覆盖：

- **计算：** 每个任务的 vCore、内存、并发、峰值和最长运行时间；
- **存储：** 历史数据量、每日增量、临时空间、副本和保留周期；
- **队列：** `online`、`etl`、`operation`、`business` 等旧队列到新区的映射；
- **网络：** 跨区读取、数据同步和外部输出带宽；
- **中间件：** MongoDB、Redis、Kafka、Prometheus容量；
- **人员：** 平台、开发、DBA、网络、安全、运维和业务验收投入；
- **窗口：** 双跑占用的额外资源以及补历史数据的资源峰值。

资源申请应基于现网监控和压测，不应只按任务数量平均估算。常驻流任务、日批大任务和交互查询需要分别测算。

### 3.4 压缩日志表退出

旧 `log_compress` 链路当前承担：

```text
default.log_audit_source → csc.ods_csc_log_audit
default.log_stats_source → csc.ods_csc_log_stats

csc.ods_csc_log_audit
  ├─→ default.dwb_md5_info
  ├─→ default.dwb_url_info
  └─→ default.dwb_domain_info
```

如果迁移后取消压缩日志表，需要分别回答：

- 新审计表是否等价承接 audit 的过滤、字段和分区语义；
- stats 数据是否也已迁移或有替代模型；
- MD5、URL、Domain 三类模型是否还需要；
- 直接读取旧表的任务改读哪里；
- 历史数据是否迁移以及保存多久。

### 3.5 数据验证

**记录摘要：** 迁移后需要验证数据是否完整、字段及统计口径是否一致、下游业务结果是否正确。目前批量校验方法、对照数据范围、差异处理方式和验收标准仍待确认，需要业务方、数据方共同确定。

#### 两类必须分别验收的校验

| 校验类别 | 校验对象 | 核心问题 | 验收证据 |
|----------|----------|----------|----------|
| A. 中间表生产校验 | 原始数据和维表加工得到的中间表，例如保留的 MD5、URL、Domain 模型 | 解析、过滤、关联、去重和聚合是否正确，分区及历史/增量数据是否完整 | 同输入条件下的新旧产出对账、业务规则样例及差异明细 |
| B. 消费同步校验 | 大数据平台查询结果，经消费程序写入 MongoDB、Redis、Kafka 的数据 | 查询选数、程序转换和实际写入是否正确，是否漏写、重复、错键或覆盖错误 | 查询结果、预期写入结果、目标端实际读回结果的逐级对账 |

两类校验分别记录状态。中间表正确不能证明消费同步正确，任务执行成功或写入接口返回成功也不能代替目标端读回校验。

**A 类执行要求：** 固定原始数据窗口、截止点、维表快照及加工版本，比较新旧中间表的业务键、重复次数、关键字段和聚合指标。增加由业务规则独立确定预期结果的样例，覆盖 JSON 展开、URL 标准化、域名匹配、未命中维表和迟到补数等情况，避免新旧结果一致但共同保留旧错误。若模型粒度改变，按双方确认的业务粒度比较，不强求物理行数一致。

**B 类执行要求：** 为每次验证指定批次ID、输入窗口和隔离目标，记录“平台查询结果 → 程序转换后的预期结果 → 目标端实际结果”。根据程序的过滤、合并、更新和删除规则推导预期输出；使用独立断言核对这些规则，不能只让同一段转换代码自证正确。目标端需要有明确的写入完成检查和等待时限。

| 目标端 | 必须核对的内容 |
|--------|----------------|
| MongoDB | 按业务键比较文档字段、类型、嵌套结构；检查 upsert、增量更新、覆盖和删除规则、重复文档、批量部分失败及重试后的最终状态。测试更新时固定初始集合状态 |
| Redis | 核对 Key 生成规则、数据类型、值、Hash/Set/ZSet 成员及分值；检查覆盖、删除和到期策略。TTL 按固定观察时点及约定容差比较，避免把自然倒计时算作差异 |
| Kafka | 用独立验证消费者读取影子 Topic 中本批次消息，按事件ID或业务键核对 Key、Payload、Schema、缺失与重复；仅在业务要求的同键/分区范围核对顺序，不要求跨分区全局有序，也不以 offset 相同为标准 |

消费端验证须覆盖正常批次、空结果、重跑、部分失败重试和迟到补数。对于允许重复投递的链路，明确重复容忍与去重责任，并验证下游处理结果，不直接承诺端到端恰好一次。

建议报告为每个任务设置三个独立结论：`上游中间表校验`、`消费查询及转换校验`、`目标端读回校验`。不依赖中间表的任务标记第一项为不适用；三区 MongoDB 等目标缺失时，第三项标记为阻塞，不计入端到端验收通过。数据负责人确认 A 类，消费任务负责人和下游业务负责人共同确认 B 类。

#### 验证方案的前置问题

**困难点：不仅需要执行验证，还需要先确定如何验证。** 部分任务可能只需修改连接或表名，但“能执行”不代表“结果正确”，查询结果一致也不代表写入下游系统的行为正确。目前尚未确认统一验证方案，不能将批量验证能力视为已经具备。

| 待解决问题 | 具体难点 | 需要落实的动作 |
|------------|----------|----------------|
| 在哪里验证 | 新旧平台连接、只读权限、执行节点及三区影子输出环境是否可用 | 确定验证执行环境；MongoDB未具备时可先验证查询，但外部写入验收保持待验证 |
| 用什么数据验证 | 新旧平台历史范围、更新时点、迟到数据和维表版本可能不同 | 固定共同可查的日期、数据截止点和维表快照；没有可比数据时先补齐基线 |
| 以什么为正确标准 | 旧表可能已停更或存在历史问题，不能无条件将旧结果视为正确答案 | 保存旧结果作为回归基线，同时由业务方确认关键样例和预期结果 |
| SQL如何批量执行 | SQL分散在配置、脚本和任务代码中，可能存在动态参数、前置步骤和UDF | 建立带任务ID、SQL版本、参数、表映射及依赖的验证清单，先提取可独立执行的只读SQL |
| 结果如何比较 | 无唯一键、重复行、浮点差异、无序结果、TopN和LIMIT导致直接比较失真 | 按业务键或保留重复次数的结果集合比较；明确数值容差，TopN固定排序及并列规则 |
| 数据量大怎么验证 | 全量双跑可能占满生产资源，抽样又可能遗漏问题 | 先检查依赖与执行计划，再按固定分区限并发试跑；汇总筛差异后定位明细，并记录验证覆盖范围 |
| 差异如何处理 | 缺数据、映射错误、SQL差异、口径变更和资源超时需要不同责任人处理 | 报告区分执行失败、结果差异、性能不达标和依赖缺失，指定责任人并支持修复后重跑 |
| 最终由谁验收 | 技术侧证明SQL可运行，业务侧才能判断结果是否符合用途 | 逐任务确定业务验收人、允许差异、观察周期和切流条件 |

建议先选取纯审计查询、关联维表查询和有外部输出的任务各一个作为代表样例，验证方法跑通后再扩展。外部输出样例需在影子目标具备后执行；只读部分通过不能替代完整任务验收。

批量报告至少保留：任务ID、新旧SQL版本、参数与数据截止点、运行状态、耗时、结果行数、差异指标、差异样例位置、原因、责任人及重跑结果。连接密钥不得写入报告。

数据验证必须与迁移并行建设，至少覆盖：

1. 字段、类型、分区、时区和 NULL 语义；
2. 按日期、小时、`app_id` 和事件类型的数据量；
3. 最大/最小事件时间、迟到数据、重复率和空值率；
4. 哈希分桶或双向差集检查；
5. 审计、统计及 MD5/URL/Domain 业务查询结果；
6. MongoDB、Redis、Kafka、Prometheus最终输出；
7. 补数、失败重试和重复执行的幂等性。

切流门槛建议定义为：连续完整业务周期对账通过，所有差异都有解释，技术负责人和业务负责人共同签字。

对于结果不一致的任务，先判断是否存在合理的数据或口径差异，再决定是否改代码。按“仅改连接、表字段映射、逻辑改造、依赖未就绪、业务确认下线”分类统计工作量，不预设所有任务都需要重构。

## 4. 推荐推进顺序

```text
阶段 0  冻结一期范围、明确责任人和不迁清单
阶段 1  补齐三区数据库、网络、权限和资源
阶段 2  确认验证方法，跑通代表样例并建立批量对账和数据就绪告警
阶段 3  批量验证改源任务，按差异补齐必要模型/兼容视图或改造逻辑
阶段 4  先迁只读查询，再迁直接消费者，最后迁 DWB 消费者
阶段 5  逐任务双跑、业务验收、切流和回滚观察
阶段 6  停止旧调度，确认无访问后再归档或删除旧表
```

每个任务必须依次通过：

```text
G0 准入：负责人、血缘、依赖和迁移价值明确
G1 数据：新旧数据对账通过
G2 任务：三区影子运行稳定，外部输出已隔离
G3 业务：关键查询和业务结果签字通过
G4 切流：监控、补数和回滚演练通过
G5 下线：观察期无异常且确认无旧表访问
```

## 5. 项目跟踪字段

每个阻塞项在周会前更新以下字段：

| 字段 | 填写要求 |
|------|----------|
| 状态 | 未开始/处理中/待确认/已解除/接受风险 |
| 责任人 | 具体姓名，不只写部门 |
| 计划完成时间 | 明确到日期 |
| 下一步动作 | 一个可验证动作 |
| 依赖方 | 需要配合的部门或系统 |
| 升级条件 | 超过什么时间或出现什么情况需要升级 |
| 证据 | 方案、测试报告、对账报告或签字记录链接 |

项目进度建议按以下数字汇报，而不是使用笼统完成百分比：

```text
范围内任务数 / 血缘确认数 / 数据对账通过数 / 业务验收数 / 已切流数 / 可下线数
P0 阻塞项数量 / 未解释数据差异数量 / 超期决策数量
```

## 6. 待立即确认事项

1. 三区目前已经具备和缺失的数据库、中间件清单；
2. 缺失 MongoDB 的建设或跨区访问方案及完成时间；

7. 计算、存储、网络和人员资源预算；

9. 旧平台停止调度与最终数据删除的时间间隔；
10. 批量验证执行环境、可比较的数据时间段、结果比较规则及试点任务；
