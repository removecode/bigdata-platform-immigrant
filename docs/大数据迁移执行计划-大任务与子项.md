# 大数据迁移执行计划：大任务与子项

编制日期：2026-09-16。状态：执行计划建议，尚未确认实际开工日、人员投入及数据湖交付日期。所有勾选项表示实际执行待办，不因本文编制完成而勾选。

## 目标与范围

业务去留明确，保留业务在StarRocks链路上数据正确、时效达标且稳定运行，退役链路有序退出，完成我方旧Hive依赖退出。平台整体下线及三区整体迁移由相关责任方统筹。

45项是任务盘点全集。7项有退出相关标记：3项原材料已下线、2项原材料可下线、phishing已确认下线待实施、log_compress计划取消。按全部退出假设剩38项，但38项仍包括接入、维护、旁路和待确认事项，不等于最终迁移开发数量。

## 时间安排总览

D1为实际启动后的第一个项目工作日；D序号不包含单列的自然日观察期。当前假设2名开发、1名测试及数据湖、运维/DBA配合，具体人员待确认。表中为阶段历时，不是人日，重叠阶段需安排人员容量，不能简单相加。

| 编号 | 大任务 | 预计历时 | 建议时间 | 关键结果 |
|---|---|---|---|---|
| T1 | 业务对齐与范围确认 | 5个工作日 | D1—D5 | 去留清单、首批范围、业务验收人 |
| T2 | 梳理保留任务完整依赖 | 3个工作日 | D3—D5 | 输入、加工、输出及业务读取依赖清单 |
| T3 | 数据湖交付与数据格式对齐 | 3个工作日完成对齐；实际交付另排 | D4—D6 | 表级交付协议、责任人及日期 |
| T4 | 环境与验证通路准备 | 4个工作日 | D5—D8 | 首批可执行E2E测试的环境 |
| T5 | 输入验收与代表任务试点 | 3个工作日 | D8—D10 | 首条E2E证据、性能实测及修订排期 |
| T6 | 批量改造与必要中间加工 | 7个工作日 | D11—D17 | 改造版本及中间结果验收 |
| T7 | 逐批E2E和性能验收 | 6个工作日，与T6滚动并行 | D15—D20 | 各批验收及问题闭环 |
| T8 | 问题收敛、恢复演练与切换 | 5个工作日 | D21—D25；达标批次可提前 | 全量保留迁移项完成切换 |
| T9 | 切换后业务观察 | 每批至少7个自然日，覆盖约定周期 | 各批切换后 | 观察报告及业务签字 |
| T10 | 旧依赖退出与交接 | 2个工作日 | 最后一批观察通过后 | 退出证据及运行交接 |

建议基线：25个工作日完成最后切换＋至少7个自然日观察＋2个工作日收口。数据湖实际交付、复杂模型及性能问题可能改变排期，D10必须根据试点重新估算。未通过关口的批次顺延，独立就绪批次继续推进。

## T1 业务对齐与范围确认

时间：D1—D5。牵头：项目推动者；参与：业务与任务负责人，具体人员待落实。

- [ ] T1.1 D1：向45项任务对应人员确认实际用途、运行实例、近期运行情况和真实读取者。
- [ ] T1.2 D2：确认7项退出相关任务的处置。区分历史已下线、可下线、确认下线待实施、计划取消，不能统一标成已停服。
- [ ] T1.3 D2—D3：落实两张已决定下线表的影响：ctig报告租户关联、attack-ip筛选、black-ti潜在依赖及DataX同步子任务。
- [ ] T1.4 D3：确认保留业务的重要程度、历史需求、时效、结果容差、可接受中断和恢复时间。
- [ ] T1.5 D4：明确混合任务哪些分支保留、替代或退役，确认共享消费者影响。
- [ ] T1.6 D5：评审迁移、退役、范围外及待决清单，指定业务负责人和验收人，形成首批候选。

交付：45项处置清单、业务验收要求、首批名单、未决事项及截止日。

检验：首批处置全部明确；其余未决事项有人跟进且有期限。全量未确认时只能宣布首批范围通过，不能宣称全量范围已锁定。

## T2 梳理保留任务完整依赖

时间：D3—D5。前置：对已确认保留部分先开展。牵头：任务开发负责人。

- [ ] T2.1 核对部署代码、SQL、动态配置及视图依赖，定位手工清单漏标、多标和缺证据项。
- [ ] T2.2 列出每项输入表、生产者、字段、历史窗口、更新频率和完整批次信号。
- [ ] T2.3 区分直接消费原始日志、基础表、中间结果以及原压缩表的分支。
- [ ] T2.4 落实输出位置：Mongo集群/库/集合、Redis实例/Key、Kafka集群/Topic，以及文件、指标和接口。
- [ ] T2.5 补齐输出的实际读取服务、业务场景、数据保留与失败影响。
- [ ] T2.6 标出共享加工、跨任务顺序及退役对保留链路的影响，形成批次依赖图。

交付：任务→输入→必要加工→输出→实际业务读取的依赖清单。

检验：首批所有必要分支覆盖；来源未确认、动态SQL不完整、目标不明的事项明确阻塞状态。不能以未提供SQL认定无依赖。

## T3 数据湖交付与数据格式对齐

时间：D4—D6完成对齐，实际开发同步和数据回填另设交付日期。前置：首批业务需求和依赖清楚。牵头：项目推动者、数据湖接口人。

- [ ] T3.1 找春兰对齐数据格式与新增Mongo表同步（ACT-007）：确认具体源/目标、字段名称与类型、业务键、数据样例。
- [ ] T3.2 确认全量与增量衔接、更新删除、空值、时区、同步频率及历史范围。
- [ ] T3.3 对齐audit/stat及SODL日志的目标映射与可用性；audit/stat已迁不代表其他输入已交付。
- [ ] T3.4 确认保留业务需要的Mongo/其他基础表，核实生产者，不默认全部来自DataX。
- [ ] T3.5 确认必要中间结果的生产承接方、逻辑口径、校验方法及发布规则。
- [ ] T3.6 按表登记负责人、交付日期、验收标准、依赖业务及故障变更通知方式。

交付：字段映射、样例、表级交付清单及责任边界。

检验：首批无无人承接的数据依赖，每项有交付时间。完成需求对齐不等于实际数据交付验收通过。

## T4 环境与验证通路准备

时间：D5—D8。前置：确认首批目标和资源需求。牵头：运维/DBA，开发和测试配合。

- [ ] T4.1 打通StarRocks访问、网络、账号和权限，确认计算并发与存储容量。
- [ ] T4.2 落实三区缺失Mongo目标；过渡访问如需使用，单列范围与退出安排。
- [ ] T4.3 配置隔离Mongo集合、Redis Key空间/实例、Kafka Topic及实际业务测试读取路由。
- [ ] T4.4 获取获准生产输入/旧结果样本。旧Hive测试不可用时记录重放数据来源、窗口、维表版本及迟到边界。
- [ ] T4.5 准备可重置目标初始状态，能够构造新增、更新、删除、重试、迟到和补数场景。
- [ ] T4.6 跑通输入→必要加工→真实任务→隔离输出→读回→业务使用的冒烟测试。

交付：环境及权限清单、样本清单、首批E2E冒烟记录。

检验：能够重复运行完整通路，不触发生产写入副作用。通路打通仅证明可验证，不代表结果正确。

## T5 输入验收与代表任务试点

时间：D8—D10。前置：首批输入实际交付、T4环境具备。牵头：开发、测试及业务验收人。

- [ ] T5.1 校验字段、业务键、完整窗口、历史及增量时效，确认新旧结果具备可比条件。
- [ ] T5.2 按依赖就绪和业务影响选2—3个候选；可考虑gnn-domain-hive-query-cronjob、ip-security-log-etl-prc、domain-security-log-etl-prc，候选不等于已批准切换。
- [ ] T5.3 做连接、表名、字段和SQL方言适配，保留必要业务口径。
- [ ] T5.4 提前试验压缩改原始路径的结果与规模性能，例如filter-layout-ip-seg-stat-prc；不因适合作性能试点就自动加入首批生产切换。
- [ ] T5.5 验证批量预检、对账、目标读回和报告工具，证明能发现缺输入、错数据和重复写入。
- [ ] T5.6 记录实际改造耗时、查询耗时、资源、差异定位及重跑次数；D10修订剩余排期。

交付：代表链路E2E报告、性能基线、自动化工具初版、工期修订依据。

检验：关键差异闭环、实际业务用例正确、约定时效达标。输入或环境未就绪只能做预检，不能标试点通过。

## T6 批量改造与必要中间加工

时间：D11—D17。前置：试点验证有效，相关输入按批就绪。牵头：任务开发与模型承接方。

- [ ] T6.1 按相同数据来源、改造模式和输出方式批量适配，复用连接配置及映射；禁止无差别字符串替换。
- [ ] T6.2 单独评审复杂SQL/UDF、时间和类型语义、JSON、关联、聚合及去重行为。
- [ ] T6.3 为保留消费者承接必要中间结果，验证行粒度、业务键、关联、聚合、完整发布及更新规则。
- [ ] T6.4 原压缩表消费者改读原始表或必要等价加工；不原样重建已取消压缩任务，不遗漏其保留业务逻辑。
- [ ] T6.5 处理已决定取消的表或分支。按变更后的业务标准验收，明确哪些新旧差异是预期结果。
- [ ] T6.6 生成版本化任务包、部署配置和回退版本，登记各任务状态与阻塞。

交付：改造版本、映射清单、中间结果校验报告、逐任务查询对账及问题清单。

检验：本批全部保留逻辑覆盖、依赖清楚；必要中间结果验收后，才进入下游完整验收。独立分支允许并行。

## T7 逐批E2E和性能验收

时间：D15—D20，与已完成改造批次滚动衔接。牵头：测试及业务验收人，开发配合。

- [ ] T7.1 按输入、中间结果、查询转换、输出读回、实际业务使用五层对账。
- [ ] T7.2 Mongo验证业务键与文档、新增/upsert、删除、失败重试及恢复后的状态。
- [ ] T7.3 Redis验证Key集合、类型、值、TTL、旧Key清理及实际读取。
- [ ] T7.4 Kafka验证消息键、内容、重复、约定顺序和消费效果；测试使用隔离通路。
- [ ] T7.5 文件/SCP验证内容与完整交付，指标验证数值、标签与时效，外部接口验证接收结果。
- [ ] T7.6 覆盖空结果、迟到、补数、部分失败及重跑，验证正常和峰值负载。
- [ ] T7.7 解释并关闭关键差异，业务验收人确认可切换范围。

交付：各批E2E验收矩阵、性能报告、差异闭环和业务确认。

检验：关键差异无未解释项，全部必要分支通过，时效达到约定。SQL运行成功或行数相同不能单独作为通过依据。

## T8 问题收敛、恢复演练与分批切换

时间：D21—D25收敛及最后批次切换，已通过T7的批次可提前实施。牵头：开发、运维与业务负责人。

- [ ] T8.1 修复剩余结果/性能问题，执行有针对性的回归验证。
- [ ] T8.2 演练停新写、目标状态恢复/补偿、旧任务与读取恢复及边界补数；Kafka已消费副作用另验补偿。
- [ ] T8.3 确认切换窗口、批次/位点、新旧数据边界与迟到归属，核查残留实例。
- [ ] T8.4 保证同一范围单一有效生产写者，完成任务和实际读取路由切换。
- [ ] T8.5 验证生产首轮数据、业务读取及延迟；异常按已验证方案回退并登记影响。

交付：恢复演练报告、切换记录、生产首轮对账及业务确认。

检验：本批切换后真实业务正常、边界无漏数重数，具备可执行恢复手段；切换成功不等于观察完成。

## T9 切换后业务观察

时间：每批至少7个自然日且覆盖约定业务周期；最后一批从自身切换时间起算。牵头：业务、任务负责人及运维。

- [ ] T9.1 跟踪结果变化、调度成功率、增量延迟、吞吐及资源使用。
- [ ] T9.2 检查重试、迟到、补数和目标状态是否符合预期。
- [ ] T9.3 确认业务接口、报告、规则和接收方持续正常使用。
- [ ] T9.4 低频任务覆盖实际运行周期或业务认可的等价演练，关闭关键问题。
- [ ] T9.5 业务负责人签署批次观察结论，确认旧依赖退出条件。

交付：观察报告、问题闭环、业务签字。

检验：各批均覆盖要求，不能借用其他批次观察时间，不能以无告警代替业务验收。

## T10 旧依赖退出与运行交接

时间：最后一批观察通过后2个工作日；独立退役项可在确认无保留消费者后提前处理。牵头：项目推动者、数据湖、运维。

- [ ] T10.1 核查旧Hive查询、共享接入/加工、中转供数、低频任务和跨区过渡访问。
- [ ] T10.2 停止获批旧调度；共享上游需等所有保留消费者完成退出。
- [ ] T10.3 核实历史已下线任务、落实新增退役事项，保留实际执行证据。
- [ ] T10.4 确认数据保留期限与后续清理责任，恢复期内旧供数、版本及必要数据保持可恢复。
- [ ] T10.5 交接监控、告警、运行手册、负责人及故障处理方式。
- [ ] T10.6 汇总验收证据，确认我方旧依赖退出；不将其等同于平台全局下线。

交付：旧依赖核查、停调度记录、退役验收、数据保留安排及运行交接。

检验：保留业务不存在未披露旧平台依赖，获批退出事项完成，运行责任明确。涉及停用后的额外观察或保留周期，应延后相应收口项，不能为满足2天估算跳过。

## 阶段里程碑与记录方式

| 里程碑 | 对应任务 | 建议节点 | 验收要点 |
|---|---|---|---|
| M0 范围确认 | T1、T2 | D5 | 首批全部明确；全量未决有责任人与期限 |
| M1 首批输入与E2E环境就绪 | T3、T4、T5输入验收 | D10前 | 输入验收和全链路冒烟通过 |
| M2 代表链路试点通过 | T5 | D10 | 数据/输出/性能通过，发布修订排期 |
| M3 首批生产切换成功 | 首批T7、T8 | D15—D20建议窗口 | 切换与首轮生产对账通过 |
| M4 保留迁移范围全部切换 | T6—T8全批次 | D25建议目标 | 无遗漏保留任务或分支，范围未决已闭环 |
| M5 业务观察验收通过 | T9 | 最后一批切换后至少7个自然日 | 覆盖约定业务周期并签字 |
| M6 我方旧依赖退出 | T10 | 最后观察通过后2个工作日建议目标 | 退出与运行交接证据齐备 |

每项验收记录：范围与版本、检查项、预期标准、实际结果、证据位置、未解决问题、结论、确认人及日期。结论分为通过、部分批次通过、未通过，不以经过了计划时间代替验收。

日常进度分别报告：范围确认、输入就绪、改造验证、E2E通过、已切换、观察完成与退出完成。阶段数字不相加，任务不重复计完成。阻塞需记录责任人、影响批次及预计解除日期。
